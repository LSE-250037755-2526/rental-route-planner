# 租房看房路线规划｜MVP范围说明 V1.2

## 一、项目背景

用户在短时间内集中看房时，通常需要同时处理多个房源地址、固定预约时间、交通方式、房源优先级和临时变更。目前这些信息分散在租房平台、微信聊天、中介消息和地图软件中，用户往往依靠手动查询、截图和备忘录安排路线，容易出现：

- 路线明显折返；

- 固定预约时间冲突；

- 对交通和看房时间估计不足；

- 临时改约后不知道如何重新安排；

- 看完多套房后难以记清各房源差异。

本产品定位为：

面向集中看房场景的行程协调与决策工具。

它不替代租房平台，也不替代导航软件，而是将分散的房源、预约、位置和用户约束整理成一套可理解、可执行、可调整的看房计划。

核心规划能力是在用户提供的可用日期、每日可用时段、预约时间窗口、必看程度、结束时间和打车预算等约束下，先把房源分配到允许的日期，再分别优化每个启用日期内的房源顺序与交通方式，优先生成可按时执行、公共交通效率高且成本可控的完整看房计划。

本文中，“看房计划”指覆盖一个或多个启用日期的整体计划；“单日路线”指某一个启用日期内的路线。用户提供可用日期，系统决定实际启用哪些日期，且不得使用用户未提供的日期。

## 二、首轮测试结论

首轮假产品测试支持产品继续进入MVP验证阶段，核心结论包括：

- 用户确实存在集中看房时的信息整理、时间协调和路线安排困难。

- 用户更自然的起点是“添加房源”，而不是先建立一个空白行程。

- 用户最关心的是能否按时完成预约，而不只是理论上的最短路线。

- 时间轴比纯地图更适合作为主要信息结构，地图主要帮助用户理解空间分布和折返情况。

- 用户愿意接受系统推荐，但需要看到推荐理由，并保留手动调整权。

- 临时改约、取消和延误是重要场景，但不是每次看房都会发生，因此应作为按需分支，而不是固定流程。

- 用户愿意进行简单房源记录，但不愿意填写冗长评分表。

- 用户可以接受输入信息，但对重复录入和逐项填写存在明显抵触。

因此，当前结论为：

Go，但应先通过轻量MVP验证用户是否愿意提交真实房源、采用推荐路线并在真实看房过程中持续使用。

## 三、MVP目标

MVP不是验证用户是否“觉得这个产品有用”，而是验证以下核心行为：

- 用户是否愿意录入一次真实看房所需的4—8套房源及其可用日期；

- 系统能否根据跨日预约与每日可用时段生成一套基本可执行的整体计划；

- 用户是否愿意直接采用推荐路线，或仅进行小幅修改；

- 预约发生变化后，用户是否愿意使用动态重排；

- 产品是否能够减少路线折返、预约冲突和手动规划时间；

- 用户完成一次看房后，下次是否仍愿意继续使用。

MVP的核心价值验证问题是：

用户是否愿意把真实看房行程交给产品协调，并按照产品生成的计划行动。

## 四、目标用户

核心用户

- 初到陌生城市的实习生、应届毕业生和年轻职场人；

- 通常计划在1—2天内集中看4—8套房；4—8套是V0.1A核心场景和性能验证目标，不是产品、引擎或输入校验的硬上限；

- 同时联系多个中介或公寓运营方；

- 至少有一套房源存在固定预约时间；

- 对城市地理分布和交通耗时不熟悉；

- 当前依赖地图、微信、备忘录和表格手动规划。

暂不重点覆盖

- 只看1—2套房、无需规划路线的用户；

- 长期从事租赁业务、已经形成成熟工作流程的职业中介；

- 主要进行线上看房、不需要线下移动的用户；

- 需要多人协作决策的家庭租房场景。

## 五、核心使用场景

场景一：看房前规划

用户已经收集多套房源，提供一个或多个可用日期及每日可用时段，希望系统在不改变固定预约日期的前提下，决定实际使用哪些日期、把房源分配到合适日期，并生成每个启用日期的单日路线。

场景二：看房当天执行

用户先查看整体计划和启用日期，再以当天的时间轴为主查看下一套房、预计到达时间、交通方式和预约风险；地图用于辅助理解该日的空间分布与折返情况。

场景三：行程临时变化

中介临时修改预约时间、房源取消、看房超时或用户需要提前结束，系统重新计算受影响的部分。

场景四：看房后快速记录

用户看完一套房后，用很少的信息记录候选状态和最容易忘记的优缺点。

## 六、MVP核心流程

正常主流程

添加房源 → 设置可用日期与行程条件 → 生成看房计划 → 路线中心 → 按启用日期开始看房

动态调整分支

路线中心 → 行程有变化 → 填写变化 → 查看受影响内容 → 采用新方案或手动调整 → 返回路线中心

快速记录分支

路线中心 → 点击具体房源 → 完成看房 → 快速记录 → 返回路线中心

动态调整和快速记录均为按需功能，不作为主流程中的固定步骤。

## 七、MVP功能范围

P0：必须完成的核心功能

1. 房源录入

用户可以：

- 手动填写房源地址；房源名称由地址自动生成，可选修改；

- 粘贴地图地址；

- 粘贴一段聊天内容，由系统或人工辅助识别地址和预约时间，并预填可识别信息；

- 设置看房时间窗口（固定时间 / 时间范围 / 时间灵活 / 暂未确认）；

- 标记房源重要程度（必看 / 有时间再看）；

- 中介 / 带看人（选填，用于信息留存；当前V0.1A不参与路线排序）；

- 修改或删除已添加房源。

第一版不要求实现对所有租房平台链接的稳定自动解析。无法识别时，允许用户手动补充。

前置录入只要求地址、看房时间窗口和房源重要程度；中介 / 带看人为选填，联系人、租金、详细备注不要求在生成路线前填写。单套预计看房时长默认30分钟，可后续修改。原始看房时间保留固定、范围、灵活或未确认语义；进入某个单日路线后，再针对该日标准化为 earliestStart / latestStart 开始窗口。

2. 行程条件设置

用户可以填写：

- 一个或多个可用看房日期；

- 每个可用日期的最早出发时间和最晚结束时间；

- 出发地点；

- 可选的最多启用天数或必须完成日期；

- 交通策略：尽量公共交通 / 公共交通优先，必要时打车（默认） / 效率优先，可灵活打车；

- 打车预算（可选）：不限制 / ¥50 / ¥100 / 自定义；

- 单套预计看房时间（默认30分钟，可不填写）；

- 确认房源重要程度（必看 / 有时间再看）；

- 出行偏好（可选）：少换乘 / 少走路 / 不骑远距离。

系统不要求用户逐段预先选择“公交还是打车”，也不要求用户设置“节省多少分钟才值得打车”等复杂参数；系统根据整体交通策略和预算自动比较各路段方案。

用户不需要预先决定最终使用几天。系统只能从用户提供的可用日期中选择启用日期，可以少用但不得自行增加日期。V0.1产品界面可最多暴露3个可用日期，但3天不是永久领域上限；未来扩展到更多日期不应要求重写核心规则。

3. 看房计划生成

核心目标：不追求单纯的最短距离。系统先在可用日期约束下确定房源的日期分配，再对每个启用日期联合优化“房源顺序＋交通方式”，尽量完成更多高优先级房源，同时降低迟到风险、交通耗时和不必要的打车成本。

整体计划输入包括：

- 用户提供的可用日期及每日可用时段；

- 可选的最多启用天数和必须完成日期；

- 房源位置及标准化坐标；

- 房源的原始看房时间输入，以及分配到目标日期后标准化得到的 earliestStart / latestStart 开始窗口；

- 房源重要程度（必看 / 有时间再看）；

- 预计看房时长；

- 出发地点以及适用于各单日路线的时间条件；

- 公共交通优先策略和打车预算；

- 公共交通与打车的两两路段时间、费用及公共交通换乘/步行信息；

- 固定预约缓冲时间；

- 中介 / 带看人（选填）。

P0规划规则：

- 固定日期预约只能分配到其固定日期；日期受限房源只能在其允许日期之间分配；灵活房源可在最终确认的允许日期中分配；

- 系统只可启用用户提供的可用日期，并可以在用户提供多个日期时只启用其中一部分；

- 日期分配与单日路线优化是两个独立层次：先生成日期分配候选，再分别优化每个启用日期的单日路线，最后汇总并比较整体计划；

- 先满足硬约束：时间窗口、必看房源、最早出发、最晚结束、看房时长、已完成房源及固定预约缓冲；

- 以固定时间或窄时间窗口作为时间锚点，将其他房源尝试插入可行空档；只有“当前结束时间＋去候选房源交通时间＋看房时长＋去下一时间锚点交通时间＋缓冲”不超过下一时间窗口上限时才允许插入；

- 对公共交通计算规则型迟到风险；在交通时间接近时，优先换乘更少、步行更短、缓冲更充足的方案；

- 对每条候选顺序同时比较公共交通与打车组合；默认公共交通优先，仅在避免迟到、公共交通明显绕行或能够释放额外看房时间时优先推荐关键路段打车；

- 在用户预算内比较0段、1段、2段及策略允许范围内的多段打车组合，并重新计算完整时间轴，避免只按单段“分钟/元”选择；

- 单日候选路线采用分层比较：预约可执行性 → 必看房源完成 → 当日可完成房源数 → 迟到风险 → 总交通时间 → 打车成本 → 折返/换乘/等待体验；高层目标不得被低层目标覆盖；整体计划的跨日排序政策以已确认规则和待决策门为准，不得擅自用一个加权分数替代；

- 每个单日路线输出“最省钱 / 推荐 / 最省时间”三类方案；结果重复时去重。推荐单日方案默认突出公共交通优先＋关键路段打车的平衡方案；多日整体结果最终展示一种还是多种方案仍为待决策门；

- 所有关键排序和打车推荐必须给出可理解原因，不以黑盒分数替代解释。

MVP实现以可解释规则引擎、预计算交通矩阵和有限候选搜索为主，不使用机器学习。4—8套房源是V0.1A核心场景与性能目标，可先使用DFS / 回溯搜索；搜索只负责探索候选，时间窗口、可行性、风险、预算、排序和解释等规则独立定义。规模扩大时可替换搜索策略而不重写业务规则。

4. 路线中心

路线中心代表一份完整看房计划，先展示整体启用日期与房源分配，再按启用日期展示单日路线。用户提供但未启用的日期应明确为未使用，而不是从计划中消失。

路线中心同时包含：

整体计划摘要

- 实际启用日期和启用天数；

- 每日房源数量与总体完成数量；

- 总完成数量、总交通时间和其他已确认可直接汇总的指标；整体风险如何汇总、多日打车预算如何归属仍为待决策门；

- 影响启用天数或日期分配的关键解释。

单日方案对比

当前启用日期内优先展示并可切换：

- 最省钱：以公共交通为主，打车支出最低；

- 推荐：公共交通优先，在关键路段适当打车，平衡准时、完成数量、时间和成本；

- 最省时间：在用户允许范围内更积极使用打车，以更早完成或覆盖更多房源。

每个单日方案至少展示预计结束时间、可完成房源数、总交通时间、预计打车费用和主要风险；同一结果应去重。整体计划是否另行提供最省钱 / 推荐 / 最省时间三类方案，不在当前阶段预设。

单日时间轴

作为每个启用日期内的主要信息结构，展示：

- 出发时间；

- 房源顺序；

- 预计到达时间；

- 预约时间；

- 看房时段；

- 交通方式和用时；

- 是否存在迟到或冲突风险。

- 推荐交通方式及关键打车路段；

- 预计打车费用及相对全公交节省时间；

- 公共交通可执行风险（低 / 中 / 高）。

地图

作为辅助信息结构，展示：

- 起点；

- 房源编号点位；

- 推荐路线；

- 点位和时间轴的一一对应关系。

推荐解释

每个关键安排至少显示一条简单理由，例如：

- 优先满足10:00固定预约；

- 与上一套房距离较近；

- 为下一套预约预留15分钟；

- 该房源时间灵活，因此安排在最后。

- 本段公共交通换乘较多，改为打车预计多花¥X、节省Y分钟；

- 本段打车可避免下一预约迟到；

- 本段打车可释放足够时间，使当日多完成1套房源。

5. 手动调整

用户可以：

- 调整时间灵活房源的顺序；

- 暂时移除某套房；

- 修改单套预计停留时间；

- 修改交通策略或单段交通方式；

- 修改最晚结束时间。

系统在调整后提示：

- 是否可能迟到；

- 是否存在预约冲突；

- 新的预计结束时间；

- 总交通时间变化。

固定预约房源默认不可直接拖动；如需调整，先修改预约时间。

任何手动调序或交通方式修改都必须重新计算完整后续时间轴，并即时提示是否产生时间窗口冲突、迟到风险、结束时间变化和新增打车费用。

6. 冲突提示

系统必须能够识别并提示：

- 两个固定预约无法同时满足；

- 交通时间不足；

- 某套房源的时间窗口无法满足；

- 预计结束时间超过用户限制；

- 地址无法识别；

- 某套房源与其他房源距离过远；

- 某个启用日期内无法完成已分配房源；

- 用户提供的全部可用日期仍不足以安排所有必看房源；

- 固定预约日期不在用户提供的可用日期中。

冲突出现时，不替用户静默删除房源，而是让用户选择：

- 移除某套房；

- 修改预约；

- 延长最晚结束时间；

- 保留冲突并继续。

如果用户只提供一个日期且该日无法安排全部重要房源，系统不得自动增加“明天”或其他未提供日期。系统应说明现有可用时间不足，保留明确的冲突或部分结果，并允许用户补充另一个可用日期。具体的多日部分结果类型不在本阶段擅自定义。

7. 临时变化与动态重排

MVP阶段优先支持三类高频变化：

重排调用与首次排序相同的核心算法：冻结已完成房源、当前位置和当前时间，仅对剩余房源重新执行时间窗口处理、候选顺序、公共交通/打车比较、风险判断和方案排序。

- 某套房预约时间改变；

- 某套房取消或已租出；

- 某套看房实际耗时超过预计。

重排结果只突出真正发生变化的内容，包括：

- 哪些房源时间改变；

- 哪些房源顺序改变；

- 结束时间变化；

- 是否产生新的冲突。

用户可以选择：

- 采用新方案；

- 自己调整；

- 暂不采用。

8. 简单导航承接

每套房源提供“去导航”按钮，跳转至现有地图应用。

MVP不自行开发完整的实时导航能力。

P1：建议纳入，但不作为核心上线阻塞项

9. 快速房源记录

用户完成看房后，可以记录：

- 候选；

- 待定；

- 淘汰；

- 一句话印象；

- 一个主要优点；

- 一个明显问题。

记录应控制在约30秒内完成。

10. 基础费用记录

保留可选的费用补充入口，包括：

- 月租；

- 押付方式；

- 中介费；

- 水电费类型；

- 网络费；

- 物业费。

费用字段默认折叠，并支持“稍后补充”。

详细费用记录不应阻碍路线规划和看房执行主流程。

11. 历史计划（P1）

在路线与记录功能稳定后支持查看已完成计划，用于复盘和后续比较；不阻塞首版MVP上线。

12. 路线增强能力（P1）

以下能力保留为P1/延期规格，不属于当前V0.1A Core Engine完成条件：

- 路线机会成本：对非必看房源比较“包含该房源 vs 不包含该房源”的路线差异，提示新增交通时间、结束时间变化及是否导致其他房源无法完成；必看房源只提示影响，不自动移除。

- 同一中介 / 带看人作为软约束（Case 12）：未来P1仅可在更高层目标基本相同的方案中用作低层并列偏好，不得覆盖时间窗口、必看和准时约束；当前V0.1A不实现该排序规则。

- Plan B：对全程最紧张的1—2个高风险节点预生成备用方案，例如“延误后本段改打车”或“先去固定预约、将灵活房源后移”；备用方案仍使用同一套排序规则。

## 八、本轮明确不做

为控制开发成本和验证范围，以下功能不进入第一版MVP：

- 自营房源搜索和房源交易；

- 自动联系中介或自动预约；

- 完整聊天系统；

- 多人共同编辑和家庭协作；

- 复杂房源评分模型；

- AI自动判断哪套房最值得租；

- 合同审核和签约管理；

- 支付、定金或租金交易；

- 独立实时导航系统；

- 精确的实时公交到站预测；

- 覆盖所有租房平台的链接解析；

- 大规模图片识别和户型分析；

- 房源照片、语音的智能总结；

- 完整租房预算和财务管理；

- 社区、内容和社交功能；

- 会员体系和复杂商业化功能。

## 九、MVP产品形态

第一版建议采用：

移动端优先网页（Next.js）＋地图API＋规则引擎＋必要的人工辅助后台；本轮不开发原生App，微信小程序待真实验证后再评估。

不建议第一阶段直接开发完整原生App。

计划技术栈：Next.js＋TypeScript＋Tailwind CSS；产品阶段可使用LocalStorage保存本地计划，后续接入高德地图API，并在需要跨设备同步时再评估Supabase；代码使用GitHub管理。实现顺序上，必须先完成并验收纯TypeScript的单日与多日核心引擎，再开始实质性产品UI或持久化工作。详细顺序只在 `docs/CORE_ENGINE_BACKLOG.md` 维护。

推荐原因

- 用户使用频率相对低，不一定愿意下载安装独立App；

- 网页或小程序更适合临时、高决策压力场景；

- 便于快速修改路线规则；

- 可以先通过人工后台验证需求，再决定是否投入复杂算法；

- 更容易在真实看房用户中进行小规模测试。

## 十、技术实现原则

路线逻辑

第一版以可解释的约束优化为核心，不追求单纯最短距离，也不使用机器学习。

- 每个单日路线使用独立日期和同日时间轴；原始看房时间在房源分配到目标日期后，标准化为 earliestStart / latestStart 开始窗口。固定预约的两个开始边界相同，时间范围直接形成边界，“某时前看完”根据看房时长换算最晚开始时间。

- 多日规划与单日路线优化分层：根据用户提供的可用日期推导房源允许日期，搜索房源日期分配，分别优化各启用日期，再汇总比较整体计划。

- 交通数据获取、provider和交通矩阵构建位于路线引擎之外；单日优化器只读取预计算的交通矩阵，不得在搜索、模拟或排序中调用provider或地图API。

- 对V0.1A核心场景的4—8套房源预计算两两交通矩阵后，可采用DFS / 回溯探索候选并调用独立的硬约束评估器剪枝；4—8不是输入上限，后续规模扩大可替换为Branch and Bound、Beam Search或其他策略。

- 交通方式是否合法、预算是否有效属于业务规则；具体枚举哪些合法交通组合属于可替换的搜索策略。每个被评估的组合都必须模拟完整单日时间轴后再比较，而不是先排顺序再局部选交通方式。

- 候选方案使用分层比较而非单一加权总分：硬约束 → 完成效率 → 可执行性 → 交通效率 → 成本效率 → 体验。

- 公共交通风险、明显绕行和打车推荐阈值作为可配置常量保存，首版使用规则阈值，真实测试后再校准，不暴露给普通用户填写。

- 临时变化属于后续能力。当前已确认的重排规则仍是冻结已完成房源、当前位置和当前时间，并复用同一单日路线规则；是否允许把未来灵活房源跨日重新分配仍为待决策事项。

人工辅助

MVP测试阶段允许：

- 人工检查地址识别；

- 人工修正明显不合理的路线或交通数据；

- 人工协助处理复杂预约冲突；

- 人工补充系统暂时不能解析的信息。

人工辅助用于验证路线排序是否真正帮助用户完成集中看房；不得用人工结果掩盖可重复出现的算法或数据错误。

## 十一、关键验证指标

以下为建议的下一阶段验证指标，不是首轮测试已经取得的数据。

核心指标

| 环节 | 指标 | 建议积极信号 |
| --- | --- | --- |
| 房源录入 | 完成添加4套以上房源的用户比例 | ≥70% |
| 路线生成 | 成功生成无严重冲突路线的比例 | ≥85% |
| 路线采用 | 直接采用或仅小幅调整的比例 | ≥60% |
| 执行效果 | 固定预约按时到达比例 | ≥85% |
| 手动调整 | 用户能够独立完成调整的比例 | ≥70% |
| 临时重排 | 发生变化后成功完成重排的比例 | ≥70% |
| 快速记录 | 完成至少一套房源记录的比例 | ≥40% |
| 再次使用 | 下次集中看房愿意继续使用的比例 | ≥60% |

保护性指标

同时观察：

- 平均房源录入时间；

- 地址识别失败率；

- 用户因路线不可信而完全放弃的比例；

- 系统推荐后大幅重排的比例；

- 预约迟到次数；

- 用户认为信息过多或操作复杂的比例。

- 三类路线方案的选择分布（最省钱 / 推荐 / 最省时间）；

- 推荐打车路段接受率及平均打车支出；

- 实际使用公共交通的路段占比；

- 高风险公共交通路段的实际迟到率；

- 系统推荐的可完成房源数与实际完成房源数差异。

## 十二、MVP测试方法

建议招募5—10名近期正在真实租房的用户，覆盖完整看房链路：

- 用户提交4—8套真实房源；

- 用户设置真实预约、可用日期和每日可用时段；

- 用户选择整体交通策略，并在愿意打车时设置预算；

- 系统决定实际启用日期并生成整体看房计划；对每个启用日期生成可执行的单日路线，记录用户理解、选择及修改行为；

- 系统或人工辅助生成整体计划和单日路线；

- 用户确认或调整计划；

- 用户在各启用日期执行对应单日路线；

- 记录是否迟到、是否改约、是否重排；

- 看房后观察是否愿意快速记录；

- 次日回访用户是否仍然认为产品有价值。

测试重点应以真实行为为主，而不是只询问主观意愿。

## 十三、MVP验收标准

MVP可以进入真实用户测试，需要至少满足：

- 用户能够完整添加、修改和删除房源；

- 用户能够设置固定时间、时间范围、时间灵活或暂未确认，并正确形成用于排序的时间窗口；

- 用户能够提供一个或多个可用日期及每个日期的可用时段，而无需预先决定最终启用天数；

- 系统实际启用的日期始终是用户提供日期的子集，且固定预约不会跨日期移动；

- 系统能够把允许移动的房源分配到合适日期，并分别生成每个启用日期的单日路线；

- 用户只提供一个日期且时间不足时，系统不会虚构另一个日期，而是给出可操作的不足说明；

- 路线中心能够展示整体启用日期和每日分组计划；每个启用日期内地图和时间轴一致；

- 用户能够看到每套房源的到达时间和预约风险；

- 系统能够解释关键排序原因；

- 系统能够基于公共交通与打车数据联合优化房源顺序和交通方式；

- 单日路线能够输出最省钱、推荐和最省时间方案（重复方案可去重），并展示结束时间、完成房源数、交通时间和预计打车费用；整体计划的最终方案形态仍以待决策门为准；

- 系统能够识别至少一种“值得打车”的关键路段情形：避免迟到、公共交通明显绕行或释放额外看房时间；

- 用户能够手动调整灵活房源；

- 系统能够识别明显预约冲突；

- 用户能够提交至少一种临时变化；

- 重排结果只展示变化部分；

- 用户可以采用、手动调整或拒绝重排；

- 所有主要流程均有返回路径；

- 用户可以跳转至外部地图导航；

- 核心流程不存在无法继续的死路。

快速记录和详细费用功能可以在核心路线功能稳定后再逐步开放。

## 十四、后续决策标准

进入下一阶段开发

当用户能够完成真实录入，路线采用率、预约准时率和再次使用意愿达到预设标准时，可以继续开发：

- 更稳定的聊天和链接识别；

- 更完整的动态重排；

- 房源对比；

- 费用计算；

- 历史计划；

- 分享和协作。

优化输入方式

若用户认可价值，但房源录入完成率低，应优先解决：

- 微信聊天粘贴识别；

- 截图识别；

- 房源链接解析；

- 地址自动补全。

优化路线能力

若用户愿意录入，但大量修改推荐路线，应优先解决：

- 时间窗口识别和约束准确性；

- 公共交通/打车时间与费用准确性；

- 迟到风险和缓冲规则；

- 关键打车路段推荐阈值；

- 路线机会成本与方案解释；

- 用户手动调序后的实时重算质量。

考虑调整产品定位

若真实用户认可问题，但个人用户使用频率过低，可考虑转向：

- 租房平台附加工具；

- 长租公寓运营工具；

- 房产中介带看排程工具；

- 企业实习生或校招员工租房服务。

## 十五、MVP范围总结

本MVP只聚焦一条核心价值链：

将多个分散房源、预约日期和看房时间窗口转化为可执行的整体看房计划：只从用户提供的日期中选择实际启用日期，把房源分配到允许的日期，以公共交通为默认方式优化每个启用日期内的房源顺序与关键路段打车选择，并在行程变化时快速重新协调。

第一版不追求功能完整，也不追求复杂AI，而是验证：

用户是否愿意录入真实房源和时间窗口、信任“房源顺序＋交通方式”的推荐方案、按照计划执行，并在下一次集中看房时继续使用。
