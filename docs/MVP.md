# 租房看房路线规划｜MVP范围说明 V1.2

## 一、项目背景

用户在短时间内集中看房时，通常需要同时处理多个房源地址、固定预约时间、交通方式、房源优先级和临时变更。目前这些信息分散在租房平台、微信聊天、中介消息和地图软件中，用户往往依靠手动查询、截图和备忘录安排路线，容易出现：

- 路线明显折返；

- 固定预约时间冲突；

- 对交通和看房时间估计不足；

- 临时改约后不知道如何重新安排；

- 看完多套房后难以记清各房源差异。

本产品定位为：

面向集中看房场景的行程协调与决策工具。

它不替代租房平台，也不替代导航软件，而是将分散的房源、预约、位置和用户约束整理成一套可理解、可执行、可调整的看房计划。

核心路线能力是在预约时间窗口、必看程度、最晚结束时间和打车预算等约束下，联合优化房源顺序与交通方式，优先生成可按时执行、公共交通效率高且成本可控的看房计划。

## 二、首轮测试结论

首轮假产品测试支持产品继续进入MVP验证阶段，核心结论包括：

- 用户确实存在集中看房时的信息整理、时间协调和路线安排困难。

- 用户更自然的起点是“添加房源”，而不是先建立一个空白行程。

- 用户最关心的是能否按时完成预约，而不只是理论上的最短路线。

- 时间轴比纯地图更适合作为主要信息结构，地图主要帮助用户理解空间分布和折返情况。

- 用户愿意接受系统推荐，但需要看到推荐理由，并保留手动调整权。

- 临时改约、取消和延误是重要场景，但不是每次看房都会发生，因此应作为按需分支，而不是固定流程。

- 用户愿意进行简单房源记录，但不愿意填写冗长评分表。

- 用户可以接受输入信息，但对重复录入和逐项填写存在明显抵触。

因此，当前结论为：

Go，但应先通过轻量MVP验证用户是否愿意提交真实房源、采用推荐路线并在真实看房过程中持续使用。

## 三、MVP目标

MVP不是验证用户是否“觉得这个产品有用”，而是验证以下核心行为：

- 用户是否愿意录入一次真实看房所需的4—8套房源；

- 系统能否根据预约约束生成一套基本可执行的行程；

- 用户是否愿意直接采用推荐路线，或仅进行小幅修改；

- 预约发生变化后，用户是否愿意使用动态重排；

- 产品是否能够减少路线折返、预约冲突和手动规划时间；

- 用户完成一次看房后，下次是否仍愿意继续使用。

MVP的核心价值验证问题是：

用户是否愿意把真实看房行程交给产品协调，并按照产品生成的计划行动。

## 四、目标用户

核心用户

- 初到陌生城市的实习生、应届毕业生和年轻职场人；

- 计划在1—2天内集中看4—8套房；

- 同时联系多个中介或公寓运营方；

- 至少有一套房源存在固定预约时间；

- 对城市地理分布和交通耗时不熟悉；

- 当前依赖地图、微信、备忘录和表格手动规划。

暂不重点覆盖

- 只看1—2套房、无需规划路线的用户；

- 长期从事租赁业务、已经形成成熟工作流程的职业中介；

- 主要进行线上看房、不需要线下移动的用户；

- 需要多人协作决策的家庭租房场景。

## 五、核心使用场景

场景一：看房前规划

用户已经收集多套房源，希望结合预约时间、起点、交通方式和最晚结束时间，生成当天的看房路线。

场景二：看房当天执行

用户以时间轴为主查看下一套房、预计到达时间、交通方式和预约风险，地图用于辅助理解空间分布与折返情况。

场景三：行程临时变化

中介临时修改预约时间、房源取消、看房超时或用户需要提前结束，系统重新计算受影响的部分。

场景四：看房后快速记录

用户看完一套房后，用很少的信息记录候选状态和最容易忘记的优缺点。

## 六、MVP核心流程

正常主流程

添加房源 → 设置行程条件 → 路线中心（点击“生成看房路线”后自动进入） → 开始看房

动态调整分支

路线中心 → 行程有变化 → 填写变化 → 查看受影响内容 → 采用新方案或手动调整 → 返回路线中心

快速记录分支

路线中心 → 点击具体房源 → 完成看房 → 快速记录 → 返回路线中心

动态调整和快速记录均为按需功能，不作为主流程中的固定步骤。

## 七、MVP功能范围

P0：必须完成的核心功能

1. 房源录入

用户可以：

- 手动填写房源地址；房源名称由地址自动生成，可选修改；

- 粘贴地图地址；

- 粘贴一段聊天内容，由系统或人工辅助识别地址和预约时间，并预填可识别信息；

- 设置看房时间窗口（固定时间 / 时间范围 / 时间灵活 / 暂未确认）；

- 标记房源重要程度（必看 / 有时间再看）；

- 中介 / 带看人（选填，用于同等可行方案下的连续安排）；

- 修改或删除已添加房源。

第一版不要求实现对所有租房平台链接的稳定自动解析。无法识别时，允许用户手动补充。

前置录入只要求地址、看房时间窗口和房源重要程度；中介 / 带看人为选填，联系人、租金、详细备注不要求在生成路线前填写。单套预计看房时长默认30分钟，可后续修改。系统内部将看房时间统一转换为 earliestTime + latestTime，用于路线排序。

2. 行程条件设置

用户可以填写：

- 看房日期；

- 出发地点；

- 最早出发时间；

- 最晚结束时间；

- 交通策略：尽量公共交通 / 公共交通优先，必要时打车（默认） / 效率优先，可灵活打车；

- 打车预算（可选）：不限制 / ¥50 / ¥100 / 自定义；

- 单套预计看房时间（默认30分钟，可不填写）；

- 确认房源重要程度（必看 / 有时间再看）；

- 出行偏好（可选）：少换乘 / 少走路 / 不骑远距离。

系统不要求用户逐段预先选择“公交还是打车”，也不要求用户设置“节省多少分钟才值得打车”等复杂参数；系统根据整体交通策略和预算自动比较各路段方案。

3. 路线生成

核心目标：不追求单纯的最短距离，而是在时间窗口、必看程度、最晚结束时间和打车预算等约束下，联合优化“房源顺序＋交通方式”，尽量在短时间内完成更多高优先级房源，同时降低迟到风险、交通耗时和不必要的打车成本。

路线输入包括：

- 房源位置及标准化坐标；

- 看房时间窗口 earliestTime / latestTime；

- 房源重要程度（必看 / 有时间再看）；

- 预计看房时长；

- 出发地点、最早出发时间和最晚结束时间；

- 公共交通优先策略和打车预算；

- 公共交通与打车的两两路段时间、费用及公共交通换乘/步行信息；

- 固定预约缓冲时间；

- 中介 / 带看人（选填）。

P0排序规则：

- 先满足硬约束：时间窗口、必看房源、最早出发、最晚结束、看房时长、已完成房源及固定预约缓冲；

- 以固定时间或窄时间窗口作为时间锚点，将其他房源尝试插入可行空档；只有“当前结束时间＋去候选房源交通时间＋看房时长＋去下一时间锚点交通时间＋缓冲”不超过下一时间窗口上限时才允许插入；

- 对公共交通计算规则型迟到风险；在交通时间接近时，优先换乘更少、步行更短、缓冲更充足的方案；

- 对每条候选顺序同时比较公共交通与打车组合；默认公共交通优先，仅在避免迟到、公共交通明显绕行或能够释放额外看房时间时优先推荐关键路段打车；

- 在用户预算内比较0段、1段、2段及策略允许范围内的多段打车组合，并重新计算完整时间轴，避免只按单段“分钟/元”选择；

- 候选方案采用分层比较：预约可执行性 → 必看房源完成 → 当日可完成房源数 → 迟到风险 → 总交通时间 → 打车成本 → 折返/换乘/等待体验；高层目标不得被低层目标覆盖；

- 系统输出“最省钱 / 推荐 / 最省时间”三类方案；结果重复时去重。推荐方案默认突出公共交通优先＋关键路段打车的平衡方案；

- 所有关键排序和打车推荐必须给出可理解原因，不以黑盒分数替代解释。

MVP实现以可解释规则引擎、预计算交通矩阵和有限候选搜索为主，不使用机器学习；目标房源量为4—8套，可通过规则剪枝的DFS / 回溯搜索实现，后续规模扩大再评估Beam Search。

4. 路线中心

路线中心同时包含：

方案对比

顶部优先展示并可切换：

- 最省钱：以公共交通为主，打车支出最低；

- 推荐：公共交通优先，在关键路段适当打车，平衡准时、完成数量、时间和成本；

- 最省时间：在用户允许范围内更积极使用打车，以更早完成或覆盖更多房源。

每个方案至少展示预计结束时间、可完成房源数、总交通时间、预计打车费用和主要风险；同一结果应去重。

时间轴

作为主要信息结构，展示：

- 出发时间；

- 房源顺序；

- 预计到达时间；

- 预约时间；

- 看房时段；

- 交通方式和用时；

- 是否存在迟到或冲突风险。

- 推荐交通方式及关键打车路段；

- 预计打车费用及相对全公交节省时间；

- 公共交通可执行风险（低 / 中 / 高）。

地图

作为辅助信息结构，展示：

- 起点；

- 房源编号点位；

- 推荐路线；

- 点位和时间轴的一一对应关系。

推荐解释

每个关键安排至少显示一条简单理由，例如：

- 优先满足10:00固定预约；

- 与上一套房距离较近；

- 为下一套预约预留15分钟；

- 该房源时间灵活，因此安排在最后。

- 本段公共交通换乘较多，改为打车预计多花¥X、节省Y分钟；

- 本段打车可避免下一预约迟到；

- 本段打车可释放足够时间，使今日多完成1套房源。

5. 手动调整

用户可以：

- 调整时间灵活房源的顺序；

- 暂时移除某套房；

- 修改单套预计停留时间；

- 修改交通策略或单段交通方式；

- 修改最晚结束时间。

系统在调整后提示：

- 是否可能迟到；

- 是否存在预约冲突；

- 新的预计结束时间；

- 总交通时间变化。

固定预约房源默认不可直接拖动；如需调整，先修改预约时间。

任何手动调序或交通方式修改都必须重新计算完整后续时间轴，并即时提示是否产生时间窗口冲突、迟到风险、结束时间变化和新增打车费用。

6. 冲突提示

系统必须能够识别并提示：

- 两个固定预约无法同时满足；

- 交通时间不足；

- 某套房源的时间窗口无法满足；

- 预计结束时间超过用户限制；

- 地址无法识别；

- 某套房源与其他房源距离过远；

- 所有房源无法在当天完成。

冲突出现时，不替用户静默删除房源，而是让用户选择：

- 移除某套房；

- 修改预约；

- 延长最晚结束时间；

- 保留冲突并继续。

7. 临时变化与动态重排

MVP阶段优先支持三类高频变化：

重排调用与首次排序相同的核心算法：冻结已完成房源、当前位置和当前时间，仅对剩余房源重新执行时间窗口处理、候选顺序、公共交通/打车比较、风险判断和方案排序。

- 某套房预约时间改变；

- 某套房取消或已租出；

- 某套看房实际耗时超过预计。

重排结果只突出真正发生变化的内容，包括：

- 哪些房源时间改变；

- 哪些房源顺序改变；

- 结束时间变化；

- 是否产生新的冲突。

用户可以选择：

- 采用新方案；

- 自己调整；

- 暂不采用。

8. 简单导航承接

每套房源提供“去导航”按钮，跳转至现有地图应用。

MVP不自行开发完整的实时导航能力。

P1：建议纳入，但不作为核心上线阻塞项

9. 快速房源记录

用户完成看房后，可以记录：

- 候选；

- 待定；

- 淘汰；

- 一句话印象；

- 一个主要优点；

- 一个明显问题。

记录应控制在约30秒内完成。

10. 基础费用记录

保留可选的费用补充入口，包括：

- 月租；

- 押付方式；

- 中介费；

- 水电费类型；

- 网络费；

- 物业费。

费用字段默认折叠，并支持“稍后补充”。

详细费用记录不应阻碍路线规划和看房执行主流程。

11. 历史计划（P1）

在路线与记录功能稳定后支持查看已完成计划，用于复盘和后续比较；不阻塞首版MVP上线。

12. 路线增强能力（P1）

- 路线机会成本：对非必看房源比较“包含该房源 vs 不包含该房源”的路线差异，提示新增交通时间、结束时间变化及是否导致其他房源无法完成；必看房源只提示影响，不自动移除。

- 同一中介 / 带看人作为软约束：仅在更高层目标基本相同的方案中优先连续安排，不得覆盖时间窗口、必看和准时约束。

- Plan B：对全程最紧张的1—2个高风险节点预生成备用方案，例如“延误后本段改打车”或“先去固定预约、将灵活房源后移”；备用方案仍使用同一套排序规则。

## 八、本轮明确不做

为控制开发成本和验证范围，以下功能不进入第一版MVP：

- 自营房源搜索和房源交易；

- 自动联系中介或自动预约；

- 完整聊天系统；

- 多人共同编辑和家庭协作；

- 复杂房源评分模型；

- AI自动判断哪套房最值得租；

- 合同审核和签约管理；

- 支付、定金或租金交易；

- 独立实时导航系统；

- 精确的实时公交到站预测；

- 覆盖所有租房平台的链接解析；

- 大规模图片识别和户型分析；

- 房源照片、语音的智能总结；

- 完整租房预算和财务管理；

- 社区、内容和社交功能；

- 会员体系和复杂商业化功能。

## 九、MVP产品形态

第一版建议采用：

移动端优先网页（Next.js）＋地图API＋规则引擎＋必要的人工辅助后台；本轮不开发原生App，微信小程序待真实验证后再评估。

不建议第一阶段直接开发完整原生App。

计划技术栈：Next.js＋TypeScript＋Tailwind CSS；V0.1使用LocalStorage保存本地计划，V0.2接入高德地图API，后续需要跨设备同步时再引入Supabase；代码使用GitHub管理。

推荐原因

- 用户使用频率相对低，不一定愿意下载安装独立App；

- 网页或小程序更适合临时、高决策压力场景；

- 便于快速修改路线规则；

- 可以先通过人工后台验证需求，再决定是否投入复杂算法；

- 更容易在真实看房用户中进行小规模测试。

## 十、技术实现原则

路线逻辑

第一版以可解释的约束优化为核心，不追求单纯最短距离，也不使用机器学习。

- 将所有看房时间统一为 earliestTime / latestTime；固定预约等价于两个时间值相同，时间范围和“某时前看完”转换为可计算的窗口。

- 地图服务只负责地址、坐标、公共交通/打车时间和费用等基础数据；排序规则独立封装，避免与地图API耦合。

- 对4—8套房源预计算两两交通矩阵后，采用DFS / 回溯＋硬约束剪枝生成可行顺序；若后续房源规模扩大再切换Beam Search等近似搜索。

- 每个候选顺序在交通策略和预算允许范围内枚举交通方式组合，并模拟完整时间轴后再比较，而不是先排顺序再局部选交通方式。

- 候选方案使用分层比较而非单一加权总分：硬约束 → 完成效率 → 可执行性 → 交通效率 → 成本效率 → 体验。

- 公共交通风险、明显绕行和打车推荐阈值作为可配置常量保存，首版使用规则阈值，真实测试后再校准，不暴露给普通用户填写。

- 临时变化复用同一优化器，只冻结已完成房源、当前位置和当前时间后重新计算剩余部分。

人工辅助

MVP测试阶段允许：

- 人工检查地址识别；

- 人工修正明显不合理的路线或交通数据；

- 人工协助处理复杂预约冲突；

- 人工补充系统暂时不能解析的信息。

人工辅助用于验证路线排序是否真正帮助用户完成集中看房；不得用人工结果掩盖可重复出现的算法或数据错误。

## 十一、关键验证指标

以下为建议的下一阶段验证指标，不是首轮测试已经取得的数据。

核心指标

| 环节 | 指标 | 建议积极信号 |
| --- | --- | --- |
| 房源录入 | 完成添加4套以上房源的用户比例 | ≥70% |
| 路线生成 | 成功生成无严重冲突路线的比例 | ≥85% |
| 路线采用 | 直接采用或仅小幅调整的比例 | ≥60% |
| 执行效果 | 固定预约按时到达比例 | ≥85% |
| 手动调整 | 用户能够独立完成调整的比例 | ≥70% |
| 临时重排 | 发生变化后成功完成重排的比例 | ≥70% |
| 快速记录 | 完成至少一套房源记录的比例 | ≥40% |
| 再次使用 | 下次集中看房愿意继续使用的比例 | ≥60% |

保护性指标

同时观察：

- 平均房源录入时间；

- 地址识别失败率；

- 用户因路线不可信而完全放弃的比例；

- 系统推荐后大幅重排的比例；

- 预约迟到次数；

- 用户认为信息过多或操作复杂的比例。

- 三类路线方案的选择分布（最省钱 / 推荐 / 最省时间）；

- 推荐打车路段接受率及平均打车支出；

- 实际使用公共交通的路段占比；

- 高风险公共交通路段的实际迟到率；

- 系统推荐的可完成房源数与实际完成房源数差异。

## 十二、MVP测试方法

建议招募5—10名近期正在真实租房的用户，覆盖完整看房链路：

- 用户提交4—8套真实房源；

- 用户设置真实预约和时间约束；

- 用户选择整体交通策略，并在愿意打车时设置预算；

- 系统同时生成最省钱、推荐和最省时间方案，记录用户理解、选择及修改行为；

- 系统或人工辅助生成路线；

- 用户确认或调整路线；

- 用户在真实看房当天执行；

- 记录是否迟到、是否改约、是否重排；

- 看房后观察是否愿意快速记录；

- 次日回访用户是否仍然认为产品有价值。

测试重点应以真实行为为主，而不是只询问主观意愿。

## 十三、MVP验收标准

MVP可以进入真实用户测试，需要至少满足：

- 用户能够完整添加、修改和删除房源；

- 用户能够设置固定时间、时间范围、时间灵活或暂未确认，并正确形成用于排序的时间窗口；

- 系统能够生成地图和时间轴一致的路线；

- 用户能够看到每套房源的到达时间和预约风险；

- 系统能够解释关键排序原因；

- 系统能够基于公共交通与打车数据联合优化房源顺序和交通方式；

- 系统能够输出最省钱、推荐和最省时间方案（重复方案可去重），并展示结束时间、完成房源数、交通时间和预计打车费用；

- 系统能够识别至少一种“值得打车”的关键路段情形：避免迟到、公共交通明显绕行或释放额外看房时间；

- 用户能够手动调整灵活房源；

- 系统能够识别明显预约冲突；

- 用户能够提交至少一种临时变化；

- 重排结果只展示变化部分；

- 用户可以采用、手动调整或拒绝重排；

- 所有主要流程均有返回路径；

- 用户可以跳转至外部地图导航；

- 核心流程不存在无法继续的死路。

快速记录和详细费用功能可以在核心路线功能稳定后再逐步开放。

## 十四、后续决策标准

进入下一阶段开发

当用户能够完成真实录入，路线采用率、预约准时率和再次使用意愿达到预设标准时，可以继续开发：

- 更稳定的聊天和链接识别；

- 更完整的动态重排；

- 房源对比；

- 费用计算；

- 历史计划；

- 分享和协作。

优化输入方式

若用户认可价值，但房源录入完成率低，应优先解决：

- 微信聊天粘贴识别；

- 截图识别；

- 房源链接解析；

- 地址自动补全。

优化路线能力

若用户愿意录入，但大量修改推荐路线，应优先解决：

- 时间窗口识别和约束准确性；

- 公共交通/打车时间与费用准确性；

- 迟到风险和缓冲规则；

- 关键打车路段推荐阈值；

- 路线机会成本与方案解释；

- 用户手动调序后的实时重算质量。

考虑调整产品定位

若真实用户认可问题，但个人用户使用频率过低，可考虑转向：

- 租房平台附加工具；

- 长租公寓运营工具；

- 房产中介带看排程工具；

- 企业实习生或校招员工租房服务。

## 十五、MVP范围总结

本MVP只聚焦一条核心价值链：

将多个分散房源和看房时间窗口转化为可执行的看房计划，以公共交通为默认方式，联合优化房源顺序与关键路段打车选择，并在行程变化时快速重新协调。

第一版不追求功能完整，也不追求复杂AI，而是验证：

用户是否愿意录入真实房源和时间窗口、信任“房源顺序＋交通方式”的推荐方案、按照计划执行，并在下一次集中看房时继续使用。
