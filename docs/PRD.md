# 租房看房路线规划｜MVP产品需求文档 PRD

版本： V1.2

产品阶段： MVP真实场景验证

产品形态： 移动端优先网页（Next.js）；本轮不开发原生App，微信小程序待真实验证后再评估

文档目标： 明确第一版产品功能、业务规则、异常状态、数据埋点和验收标准，为交互设计、开发、测试及AI辅助编程任务拆解提供依据。

## 一、产品概述

### 1.1 产品背景

用户在1—2天内集中看多套房时，需要同时处理：

- 多个房源地址；

- 固定时间、时间范围或灵活的看房时间；

- 地点之间的交通时间；

- 不同房源的优先级；

- 最晚结束时间；

- 临时改约、取消和看房超时。

目前这些信息通常分散在租房平台、微信、中介消息、地图软件和备忘录中。用户需要反复切换工具、手动计算路线，容易出现明显折返、迟到、预约冲突和信息遗忘。

### 1.2 产品定位

面向集中看房场景的行程协调与决策工具。

产品不提供房源交易，也不替代地图导航，主要负责：

- 整理分散房源和预约信息；

- 生成基本可执行的看房计划；

- 展示路线、时间轴和推荐理由；

- 在行程变化后协助重新安排；

- 支持轻量看房记录。

核心路线能力：在预约时间窗口、必看程度、最晚结束时间和打车预算等约束下，联合优化“房源顺序＋交通方式”，优先生成可执行、公共交通效率高且成本可控的看房计划。

### 1.3 产品价值

帮助用户完成：

从“我有很多分散的房源和预约”，到“我知道今天按照什么顺序、什么时间、用什么交通方式去看房”。

## 二、产品目标

### 2.1 MVP核心目标

验证用户是否愿意：

- 录入真实看房所需的4—8套房源；

- 提交真实的预约和时间约束；

- 采用系统生成的路线，或只进行小幅修改；

- 在真实看房过程中继续查看路线中心；

- 发生临时变化时使用动态重排；

- 下一次集中看房时继续使用产品。

### 2.2 非目标

MVP阶段不解决：

- 房源搜索和房源交易；

- 自动联系中介或自动预约；

- 完整实时导航；

- 租房合同审核；

- 支付、定金或租金交易；

- 多人协作；

- 复杂房源评分模型；

- AI自动选择最终租赁房源；

- 完整租房财务管理。

## 三、目标用户

### 3.1 核心用户

- 初到陌生城市的实习生、毕业生和年轻职场人；

- 计划在1—2天内集中看4—8套房；

- 同时与多个中介或公寓方沟通；

- 至少存在一套固定时间预约；

- 不熟悉当地地理位置和交通时间；

- 当前使用微信、地图、截图或备忘录手动规划。

### 3.2 核心使用场景

场景A：看房前规划

用户收集了多套房源，希望结合时间窗口、必看程度、最晚结束时间和交通策略，生成可按时执行的看房顺序，并识别值得打车的关键路段。

场景B：看房当天执行

用户通过路线中心确认下一站、交通方式、预计到达时间和预约风险。

场景C：临时变化

中介临时改约、房源取消、看房超时或用户需要提前结束，用户需要快速重新安排。

场景D：看房后记录

用户希望在不填写长表格的情况下，记录最容易遗忘的房源印象。

## 五、核心流程

### 5.1 正常主流程

添加房源 → 设置行程条件 → 路线中心（点击“生成看房路线”后自动进入） → 开始看房

### 5.2 临时变化分支

路线中心 → 行程有变化 → 选择变化类型 → 输入变化信息 → 查看重排方案 → 采用 / 自己调整 / 暂不采用

### 5.3 房源记录分支

路线中心 → 点击具体房源 → 房源详情 → 完成看房 → 快速记录 → 返回路线中心

临时变化和房源记录均为按需入口，不作为正常主流程中的固定步骤。

## 六、模块一：房源录入

### 6.1 功能目标

帮助用户尽可能低成本地将分散房源整理到同一个计划中。

### 6.2 页面名称

添加要看的房源

### 6.3 录入方式

MVP支持以下方式：

| 录入方式 | P级 | 说明 |
| --- | --- | --- |
| 手动添加 | P0 | 用户填写地址；房源名称由地址自动生成，可选修改；补充看房时间窗口和房源重要程度 |
| 粘贴地图地址 | P0 | 系统识别并标准化地址，用户补充看房时间窗口和房源重要程度 |
| 粘贴聊天内容 | P0 | 尝试提取地址和看房时间并预填，用户只补充缺失信息 |
| 粘贴房源链接 | P1 | 可保存链接，无法解析时要求手动补充 |

MVP不要求自动解析所有租房平台链接。

### 6.4 房源字段

前置字段（生成路线前）

- 房源地址；

- 看房时间窗口：固定时间 / 时间范围 / 时间灵活 / 暂未确认；

- 房源重要程度：必看 / 有时间再看（默认“有时间再看”）。

看房时间规则

- 固定时间：必须在该时间到达，内部 earliestTime = latestTime；

- 时间范围：例如13:00—15:00均可到达，内部直接保存 earliestTime / latestTime；

- 时间灵活：默认使用本次行程可用时段作为窗口，允许系统前后调整；

- “17:00前看完”等结束型表达：根据预计看房时长倒推最晚开始时间；

- 暂未确认：可保留在计划中并标记“需确认”，不作为必须满足的固定时间约束。

固定时间 / 时间范围附加字段

- 预约日期；

- 最早可开始时间；

- 最晚可开始时间（固定时间与最早时间相同）；

- 房源名称：由地址自动生成，可选修改。

- 单套预计看房时长：默认30分钟，可后续单独修改。

后续可补充字段（不在生成路线前要求填写）

- 房源链接；

- 月租；

- 联系人；

- 联系方式；

- 备注；

- 中介 / 带看人（选填，仅作为路线软约束）；

### 6.5 房源卡片信息

每张房源卡片展示：

- 房源名称；

- 地址；

- 预约状态；

- 固定预约时间；

- 必看标签；

- 编辑；

- 删除。

### 6.6 业务规则

- 至少添加2套房源后，才能生成多房源路线。

- 房源地址必须成功识别，或由用户手动选择候选地址。

- 固定时间或时间范围必须能够转换为有效的 earliestTime / latestTime；窗口结束不得早于窗口开始。

- 房源名称不作为前置必填，系统根据标准化地址生成默认名称。

- 单套预计看房时长默认30分钟，用户未修改时直接使用默认值。

“17:00前看完”等结束型约束在排序前根据看房时长转换为最晚开始时间；看房时长修改后必须重新计算对应窗口。

- 联系人、联系方式、月租和备注均不阻塞路线生成。

中介 / 带看人信息不阻塞路线生成，仅用于同等可行方案下的连续安排。

- 必看房源不会被系统自动移除。

- 重复地址允许保存，但系统需要提示“可能为重复房源”。

- 删除房源前需要二次确认。

- 修改固定预约后，已经生成的路线标记为“需要重新计算”。

### 6.7 地址识别状态

识别成功

显示标准化地址，用户可确认或修改。

多个候选地址

显示候选列表，由用户选择。

无法识别

提示：

暂时无法识别这个地址，请补充小区名称、道路或门牌号。

聊天内容部分识别

系统将识别出的内容预填，未识别字段由用户补充，不要求重新填写全部信息。

### 6.8 页面操作

主按钮：

下一步：设置行程

按钮可用条件：

- 至少存在2套有效房源；

- 所有房源地址已经确认；

- 固定预约信息完整。

### 6.9 验收标准

- 用户可以添加、编辑和删除房源；

- 用户可以设置固定时间、时间范围、时间灵活和暂未确认，并正确保存为可计算的时间窗口；

- 系统能够阻止地址为空的房源进入路线计算；

- 系统能够识别明显重复地址并提示；

- 修改房源后数据能够正确保存；

- 用户退出再返回时，已添加内容不丢失。

- 用户无需填写房源名称、租金、联系人或备注即可进入行程条件设置。

- 未单独设置看房时长时，系统按30分钟默认值参与路线计算。

## 七、模块二：行程条件设置

### 7.1 功能目标

获取生成可执行路线所需的时间、交通和房源重要程度约束。

### 7.2 页面名称

设置今天的看房条件

### 7.3 输入字段

| 字段 | 必填 | 默认值 |
| --- | --- | --- |
| 看房日期 | 是 | 最近一次固定预约日期 |
| 出发地点 | 是 | 当前定位或用户手动填写 |
| 最早出发时间 | 是 | 09:00 |
| 最晚结束时间 | 是 | 18:00 |
| 单套预计看房时长 | 否 | 30分钟（系统默认，可修改） |
| 交通策略 | 是 | 公共交通优先，必要时打车 |
| 打车预算 | 否 | 不限制；可选¥50 / ¥100 / 自定义 |
| 提前为固定预约预留多少时间 | 否 | 15分钟（默认） |
| 时间灵活的房源可以前后调整 | 否 | 默认允许 |
| 少换乘 / 少走路 / 不骑远距离 | 否 | 默认不选 |

### 7.4 交通策略

用户不需要逐段提前选择交通方式，而是先选择整体策略：

- 尽量公共交通：主方案原则上使用公共交通；仅当公共交通无法满足时间窗口时，在备选方案中提示必要打车；

- 公共交通优先，必要时打车（默认）：系统主动比较各路段公共交通与打车，仅在避免迟到、公共交通明显绕行或能够释放额外看房时间时优先推荐打车；

- 效率优先，可灵活打车：在预算允许范围内更积极使用打车，以提高当日完成房源数或缩短结束时间。

允许打车时，用户仅需设置可选的总打车预算；不要求填写“节省多少分钟才值得打车”“最多换乘几次”等高级阈值。

### 7.5 业务规则

- 最晚结束时间必须晚于最早出发时间。

- 固定时间或时间窗口必须按其可行区间安排，系统不提供“是否优先”的普通开关。

- 时间灵活及较宽时间窗口房源可以在不违反窗口上限的前提下前后移动。

- 必看房源必须尽量安排；无法安排时必须明确提示。

- 固定预约前默认预留15分钟缓冲。

- 看房时长适用于全部房源，用户可在房源详情中单独修改。

- 用户必须选择一种交通策略；选择允许打车时，未填写预算视为“不限制预算”。

- 用户未设置看房时长时使用30分钟默认值。

- “少换乘 / 少走路 / 不骑远距离”以及同一中介连续，仅用于更高层目标基本一致的方案排序，不得覆盖时间窗口、必看、最晚结束等硬约束。

### 7.6 条件冲突提示

固定预约早于出发时间

提示：

第一套固定预约早于当前出发时间，请提前出发或修改预约。

结束时间过早

提示：

当前结束时间可能无法完成所有房源，仍可生成方案并查看取舍建议。

时间窗口无效

提示：

最晚可开始时间早于最早可开始时间，请检查看房时间设置。

多个预约跨日期

提示：

当前房源包含不同日期的预约，请选择本次要规划的看房日期。

### 7.7 页面操作

主按钮：

生成看房路线

点击后：

- 保存全部条件；

- 进入路线计算状态；

- 成功后进入路线中心；

- 失败时展示具体原因和解决方式。

### 7.8 验收标准

- 所有必填字段具有校验；

- 时间逻辑错误时不能直接生成路线；

- 用户可以选择整体交通策略，并可在允许打车时设置总打车预算；

- 系统能够正确读取必看和固定预约房源；

- 系统能够正确读取并转换固定时间、时间范围、灵活时间和结束型时间约束；

- 用户修改条件后可以重新生成路线。

### 7.9 用户文案约束

- 界面避免使用“锁定顺序、时间预算、优先级、路线偏好”等抽象术语，统一使用以下生活化表达：

- “锁定时间” → “必须在这个时间到达”；

- “锁定顺序” → “必须先看这套”；

- “时间预算” → “最晚几点结束”；

- “优先级” → “必看 / 有时间再看”；

- “路线偏好” → “少换乘 / 少走路 / 不骑远距离”。

- “可接受交通方式” → “今天更希望怎么出行？”；“固定/灵活”内部统一使用时间窗口计算，但界面继续使用生活化表达。

## 八、模块三：路线生成

### 8.1 功能目标

系统默认不追求单纯的“最短路线”，而是在预约时间窗口、必看程度、最晚结束时间和打车预算等约束下，联合优化“房源顺序＋交通方式”，尽量在短时间内完成更多高优先级房源，同时降低迟到风险、交通耗时和不必要的打车成本。

### 8.2 输入数据

路线生成读取：

- 出发地点、最早出发时间、最晚结束时间；

- 房源标准地址和坐标；

- earliestTime / latestTime 时间窗口；

- 房源重要程度（必看 / 有时间再看）；

- 预计看房时长；

- 交通策略和可选打车预算；

- 固定预约缓冲时间；

- 中介 / 带看人（选填）；

- 两两地点之间公共交通与打车的时间、费用、公共交通换乘次数和步行距离。

### 8.3 时间窗口统一模型

所有房源在排序前统一转换为 earliestTime / latestTime。固定时间的两个值相同；时间范围直接使用上下限；“下午均可”等生活化输入按产品预设转换；“17:00前看完”等结束型约束根据预计看房时长倒推最晚开始时间。暂未确认房源可参与候选排序，但不得作为必须满足的固定时间锚点。

### 8.4 交通矩阵

地图 / 交通服务应在排序前尽量一次性预计算“起点＋全部房源”之间的两两交通数据，避免在候选搜索过程中重复调用API。每条 TravelEdge 至少包括公共交通时间、公共交通费用、换乘次数、步行距离，以及打车时间和预计费用。

### 8.5 硬约束与时间锚点

硬约束优先于一切效率和成本指标，包括：时间窗口可满足、必看房源原则上保留、不能早于最早出发、尽量不晚于最晚结束、已完成房源不可重排、看房时长和固定预约缓冲必须计入时间轴。固定时间或较窄时间窗口优先形成时间锚点。

### 8.6 候选顺序与空档插入

系统以时间锚点为骨架，将其他房源尝试插入锚点之间或前后。候选房源只有满足以下可行性条件时才允许插入：

当前房源结束时间 + 去候选房源交通时间 + 候选房源看房时长 + 去下一时间锚点交通时间 + 安全缓冲 ≤ 下一时间窗口的最晚允许时间。

系统主动识别固定预约之间的可利用空档，并优先放入能够提高当日完成数量且不增加迟到风险的房源。目标房源量为4—8套，V1可采用DFS / 回溯＋硬约束剪枝生成可行候选；后续规模扩大再评估Beam Search。

### 8.7 公共交通可执行风险

公共交通不只使用API给出的预计时间，还计算规则型风险。V1建议采用可配置分值：换乘≥2次 +2；步行≥800米 +1；到下一时间窗口的缓冲<10分钟 +2、10—15分钟 +1；若API能够识别高公交占比或复杂接驳，可额外 +1。riskScore 0—1=低、2=中、≥3=高。真实用户测试后再校准阈值。

当两个方案交通时间接近时，应优先风险更低、缓冲更充足的方案，使目标从“理论最快”变为“最可能按计划完成”。

### 8.8 房源顺序＋交通方式联合优化

系统不能长期采用“先排顺序、再选公交/打车”的串行逻辑，因为交通方式可能改变最佳房源顺序。对每个候选顺序，系统在交通策略和预算允许范围内生成交通方式组合，并重新模拟完整时间轴。

- 尽量公共交通：主方案不主动加入打车；若公共交通无法满足关键时间窗口，可在备选/Plan B中提示必要打车。

- 公共交通优先，必要时打车：默认比较0段、1段、2段打车及预算允许的关键组合。

- 效率优先，可灵活打车：可比较更多打车组合，仍受总预算约束。

由于4—8套房源的路段数量有限，交通方式组合可以在预计算交通矩阵后本地枚举，不应为每个组合重新请求地图API。

### 8.9 关键打车路段判断

打车不是因为“更快”就推荐，而是在整天行程的边际价值明显时才推荐。V1优先识别三类场景：

- 避免迟到：公共交通无法满足下一时间窗口，而打车可以满足；

- 公共交通明显绕行：首版可配置为“打车节省≥25分钟，且公共交通时间/打车时间≥1.8”或公共交通存在多次换乘；该阈值仅为内部默认值，不要求用户填写；

- 释放额外看房容量：某段改打车后，能够在最晚结束时间前多安排至少1套房，或恢复必看房源的可行性。

系统同时计算基础性价比（额外费用对应的节省时间）和行程价值（避免迟到、增加完成数量、保证必看、降低高风险交通、提前结束）；最终以行程价值优先，不简单使用“分钟/元”排序。

### 8.10 路线机会成本与同一带看人

路线机会成本：对非必看房源可额外比较“包含该房源 vs 不包含该房源”的最优结果，输出新增交通时间、结束时间变化和是否挤掉其他房源。必看房源只提示影响，不自动移除。该能力为P1，不阻塞首版核心排序。

同一中介 / 带看人作为软约束：只有在硬约束、完成数量、风险等更高层指标基本相同时，才优先连续安排；建议V1使用“总交通时间差≤10分钟”作为可配置的同等方案判定阈值。该能力为P1。

### 8.11 候选方案分层比较

最终候选方案采用字典序 / 分层比较，不将所有指标粗暴加权为一个总分：

- 第一层：硬约束——时间窗口满足、必看房源保留、最晚结束；

- 第二层：完成效率——尽量完成更多房源并充分利用时间空档；

- 第三层：可执行性——降低迟到风险并保留合理缓冲；

- 第四层：交通效率——减少总交通时间和明显折返；

- 第五层：成本效率——公共交通优先、关键段合理打车、不超过预算；

- 第六层：体验——少换乘、少步行、少等待、同中介连续。

### 8.12 输出三类方案

系统从候选结果中提取并去重三类方案：

- 最省钱：打车支出最低，通常以公共交通为主；

- 推荐方案：默认突出，在预约可执行和完成数量优先的前提下，平衡交通时间、迟到风险与打车成本；

- 最省时间：在用户交通策略和预算允许范围内尽量提前结束或完成更多房源。

每个方案至少输出：房源顺序、每段交通方式、预计出发/到达/看房时间、可完成房源数、总交通时间、预计结束时间、预计打车费用、公共交通风险和关键解释。若三类目标得到相同结果，只显示去重后的方案。

### 8.13 高风险节点Plan B（P1）

排序完成后识别全程最紧张的1—2个节点（例如buffer<15分钟或公共交通risk=高），预生成一个轻量备用方案：优先尝试将关键路段改为打车；仍不可行时，将非必看/宽时间窗口房源后移或跳过。Plan B仍调用同一排序规则，不另建一套算法。

### 8.14 路线计算状态

计算中

展示：“正在比较预约时间、公共交通和关键打车方案……”；超过5秒补充“房源较多，正在评估可执行方案”。

计算成功

进入路线中心，并默认选中“推荐方案”。

部分成功

当没有方案能够同时满足全部要求时，仍输出最接近可执行的方案，并明确标记时间窗口冲突、结束时间超限、必看无法安排或预算限制。

计算失败

仅在地址/交通数据缺失或基础输入无效等无法计算的情况下失败，并给出具体修复入口。

### 8.15 推荐解释规则

关键解释至少覆盖：为什么某房源安排在该时间段、为什么某段建议打车、为什么某房源建议移至其他日期、以及某套房的机会成本（若已计算）。示例：“B房可插入11:05—12:00且不影响14:00预约”“A→B公共交通需58分钟且换乘2次，打车约¥29可节省37分钟”“本段改打车可使今日多完成1套房”。

### 8.16 验收标准

- 相同输入和交通矩阵下，排序结果保持确定性；

- 任何推荐方案都不得无提示违反固定时间或明确时间窗口；

- 必看房源不得被系统静默删除；无法满足时必须输出冲突；

- 系统能够主动利用预约空档插入可行房源；

- 公共交通风险会影响同等时间方案的排序；

- 默认交通策略下能够比较至少全公交、单段打车和两段打车组合；

- 推荐打车时必须说明预计费用、节省时间和行程价值；

- 能够输出最省钱、推荐、最省时间方案并对重复结果去重；

- 每段交通时间和看房时长必须进入完整时间轴计算；

- 地图编号与时间轴编号一致；冲突情况下仍给出可理解的处理建议。

- 页面刷新后当前进度不会丢失。

## 十、模块五：临时变化与重排

### 10.1 功能目标

在预约、房源或用户时间发生变化后，帮助用户快速理解影响并做出决策。

### 10.2 入口

路线中心中的：

行程有变化

房源卡片更多菜单也可直接进入对应变化类型。

### 10.3 MVP支持的变化类型

P0

- 房源预约时间改变；

- 房源取消或已租出；

- 当前看房时间超过预计。

P1

- 新增房源；

- 用户出发时间改变；

- 用户需要提前结束；

- 交通方式临时变化。

### 10.4 变化录入

预约时间改变

用户选择：

- 发生变化的房源；

- 新预约时间；

- 是否仍然必看。

房源取消

用户选择：

- 取消的房源；

- 是否从今日行程移除。

看房超时

用户填写或选择：

- 实际结束时间；

- 是否已经出发前往下一套。

### 10.5 重排规则

重排与首次路线生成必须调用同一个核心优化器；系统冻结已完成房源、当前位置、当前时间和正在执行中的路段，仅更新剩余房源的时间窗口和交通候选。

- 只重新计算受变化影响的部分；

- 已经完成的房源保持不变；

- 当前正在进行的行程尽量保持；

- 新固定预约优先保证；

- 重排继续比较公共交通与打车组合，并受原交通策略及剩余打车预算约束；

- 灵活房源可以后移、前移或建议移除；

- 若预生成Plan B可直接恢复可行性，优先展示Plan B；否则再生成新的最省钱 / 推荐 / 最省时间候选。

- 不自动接受新方案；

- 用户必须做出明确选择。

### 10.6 重排结果页面

页面只重点展示真正发生变化的内容。

每项变化使用“原方案 → 新方案”表达：

- 到达时间；

- 看房时间；

- 房源顺序；

- 交通方式；

- 结束时间；

- 预计打车费用及相对原方案变化；

- 是否新增冲突。

未变化内容只显示一句：

其他房源的时间和顺序不受影响。

### 10.7 用户决策

采用新方案

- 保存重排结果；

- 更新地图和时间轴；

- 返回路线中心；

- 显示“行程已更新”。

自己调整

- 进入手动调整；

- 用户拖动灵活房源；

- 保存后返回路线中心。

暂不采用

- 不保存新路线；

- 返回原路线中心；

- 保留原方案；

- 可显示风险提醒。

### 10.8 冲突处理

若重排后仍然无法满足全部预约，系统提供选项：

- 移除一套非必看房；

- 延后灵活房源；

- 修改最晚结束时间；

- 联系中介改约；

- 保留冲突并继续。

### 10.9 验收标准

- 已完成房源不会被重新排序；

- 页面只突出变化部分；

- “采用、自己调整、暂不采用”含义清晰；

- 暂不采用后原路线保持不变；

- 采用后地图和时间轴同步更新；

- 采用后剩余打车预算、风险等级和Plan B同步更新；

- 所有路径均能返回路线中心；

- 重排不能出现无提示删除房源的情况。

| 未选择交通方式 | 请至少选择一种交通方式 |
| 预约日期不一致 | 当前房源包含不同日期预约 |
| 出发地无法识别 | 请选择准确的出发位置 |
| 打车预算无效 | 请输入非负金额，或选择“不限制” |

### 12.3 路线生成异常

| 异常 | 处理 |
| --- | --- |
| 地图API不可用 | 提示稍后重试并保留输入 |
| 交通时间获取失败 | 使用估算值并明确标记 |
| 固定预约无法满足 | 展示冲突房源和处理建议 |
| 超过最晚结束时间 | 生成风险方案，不直接失败 |
| 某房源距离过远 | 建议移至其他日期 |
| 全部路线生成失败 | 提供返回修改条件入口 |
| 公共交通数据不可用 | 无法比较时明确标记；若用户允许打车，可仅生成临时打车候选，否则提示稍后重试 |
| 打车价格数据不可用 | 仍可生成公共交通方案，但不展示费用性价比和混合交通推荐 |
| 无完全可行方案 | 输出最接近方案及违反的具体约束，不静默删除必看房源 |

### 12.4 执行过程异常

- 用户错过预约；

- 用户未点击到达但已经完成看房；

- 用户误操作跳过房源；

- 地图导航无法唤起；

- 当前时间已经晚于计划时间；

- 页面断网或刷新。

处理原则：

- 不丢失已经完成的操作；

- 允许用户手动修改状态；

- 避免强制按照理想流程操作；

- 离线情况下优先展示最近一次保存的行程。

### 12.5 保存异常

保存失败时：

- 保留本地填写内容；

- 提示重新保存；

- 不直接关闭页面；

- 避免重复创建相同记录。

### 13.3 核心指标

房源录入完成率

完成添加至少4套有效房源的用户数 ÷ 开始添加房源的用户数。

目标积极信号：≥70%。

路线生成成功率

成功生成路线的计划数 ÷ 提交路线生成的计划数。

目标积极信号：≥85%。

路线采用率

采用推荐路线或仅进行小幅调整的计划数 ÷ 成功生成路线的计划数。

目标积极信号：≥60%。

推荐方案采用率：采用系统默认“推荐方案”的计划数 ÷ 成功生成路线的计划数；首轮主要观察，不预设硬阈值。

时间窗口准时完成率：在有效时间窗口内开始看房的已执行房源数 ÷ 已执行房源数；建议积极信号≥85%。

关键打车推荐接受率：采用系统关键打车建议的路段数 ÷ 系统产生关键打车建议的路段数；首轮作为诊断指标，不作为Go/No-Go单独阈值。

固定预约准时率

按时到达固定预约的次数 ÷ 已执行固定预约次数。

目标积极信号：≥85%。

动态重排完成率

成功完成重排并返回路线中心的次数 ÷ 提交临时变化的次数。

目标积极信号：≥70%。

房源记录使用率

保存至少一套房源记录的计划数 ÷ 完成至少一套看房的计划数。

目标积极信号：≥40%。

再次使用意愿

下一次集中看房仍愿意使用的用户比例。

目标积极信号：≥60%。

需要同步监控：

- 平均添加一套房源耗时；

- 地址识别失败率；

- 路线生成平均耗时；

- 用户大幅重排路线比例；

- 固定预约迟到率；

- 因冲突而放弃整个计划的比例；

- 路线中心退出率；

- 快速记录放弃率；

- 系统推荐与用户最终顺序差异。

- 三类方案选择分布；

- 平均打车支出与公共交通路段占比；

- 高风险公共交通路段实际迟到率；

- 推荐打车段的平均节省时间和实际采用率；

- 系统预测可完成房源数与实际完成房源数差异。

## 十四、非功能性需求

### 14.1 性能

- 普通路线生成时间目标：5秒以内；

- 交通矩阵已缓存时，本地候选搜索与方案比较目标≤1秒；真实API获取时间不计入该本地计算目标。

- 超过5秒需要明确加载反馈；

- 页面主要操作响应时间目标：1秒以内；

- 输入和记录需要自动保存草稿。

### 14.2 稳定性

- 路线生成失败不能导致房源数据丢失；

- 页面刷新后恢复最近一次保存状态；

- 临时网络异常后支持重新提交；

- 防止重复生成计划和重复保存记录。

### 14.3 隐私

- 明确说明地址信息仅用于生成本次路线；

- 联系人和联系方式不默认公开；

- 不将用户行程分享给中介或第三方；

- 用户可以删除计划及相关记录。

### 14.4 可用性

- 核心主流程不超过3个主要页面；

- 快速记录必填项不超过1项；

- 所有异常提示必须提供解决操作；

- 不出现只有错误信息、没有下一步的页面。

本附录用于把PRD进一步约束为可直接拆分、实现和测试的开发任务；若与前文冲突，以前文的用户规则和优先级为准。

### 17.1 页面与路由边界

添加房源页：/；负责房源地址、看房时间和房源重要程度的录入。

行程条件页：/plan/settings；负责出发地、开始/结束时间、交通策略、可选打车预算和出行偏好。

房源详情与记录：/property/[id] 与 /property/[id]/note；记录模块不得阻塞路线主流程。

TravelEdge：fromId；toId；transitMinutes；transitCost；transferCount；walkMeters；taxiMinutes；taxiCost；dataStatus。

RouteOption：id；type=cheapest/recommended/fastest；stops[]；completedCount；mustCompletedCount；totalTravelMinutes；estimatedEndAt；taxiCost；taxiLegCount；riskLevel；explanations[]。

### 17.3 路线生成实现契约

1. 输入标准化：校验地址、日期、行程起止时间和打车预算；把所有房源时间转换为 earliestTime / latestTime，并根据预计看房时长处理“某时前看完”。

2. 交通矩阵预计算：对起点和全部房源两两生成 TravelEdge；排序函数只能读取矩阵，不得在搜索循环内直接调用地图API。

3. 候选顺序搜索：4—8套房源使用DFS / 回溯。每加入一个房源即模拟到达、等待、看房和去下一锚点的时间；一旦已确定无法满足时间窗口、最晚结束或必看可行性则剪枝。

4. 空档插入：固定时间/窄窗口作为锚点；宽窗口/灵活房源优先插入不会影响下一锚点且能提高完成数量的空档。

5. 风险计算：默认 riskScore = (transferCount>=2 ? 2 : 0) + (walkMeters>=800 ? 1 : 0) + (buffer<10 ? 2 : buffer<15 ? 1 : 0)；若API可识别复杂公交接驳可额外加1。0—1低、2中、>=3高。阈值必须集中配置，不散落在组件代码。

6. 交通方式组合：对每个可行房源顺序生成符合 transportStrategy 和 taxiBudget 的模式组合。transit_only主方案不主动用打车；transit_first默认枚举0—2段打车及必要关键组合；efficiency_first可枚举更多组合但不得超预算。

7. 打车价值判断：至少支持 reasonCode=avoid_late、transit_detour、unlock_extra_viewing。transit_detour首版内部阈值建议 minutesSaved>=25 且 transitMinutes/taxiMinutes>=1.8，或公共交通换乘>=2；阈值可配置并在真实测试后校准。

8. 完整时间轴模拟：任何交通方式组合都必须从出发开始重新计算 arrivalAt、viewingStartAt、viewingEndAt、buffer、estimatedEndAt 和 taxiCost；不得只对单段时间做局部替换。

9. 方案比较采用字典序键，而不是单一加权分：hardViolationCount（越少越好）→ mustCompletedCount（越多越好）→ completedCount → riskPenalty（越低越好）→ totalTravelMinutes → taxiCost → experiencePenalty。只有前一层相同/等价时才比较下一层。

10. 三方案提取：cheapest按可行前提下taxiCost最小；fastest按可行前提下estimatedEndAt/totalTravelMinutes最小；recommended使用上述默认字典序。三个RouteOption按房源顺序＋交通方式指纹去重。

11. 路线机会成本（P1）：对importance=if_time的房源可调用优化器计算exclude-one差分；不得对must房源自动执行移除，只显示impact。

12. 同中介软约束（P1）：仅在更高层指标等价且总交通时间差<=10分钟时，通过降低experiencePenalty优先连续安排同agentName房源。

13. Plan B（P1）：选择buffer<15分钟或riskLevel=high的1—2个节点，先尝试关键路段改打车；仍不可行时再尝试后移/跳过非必看宽窗口房源。

14. 动态重排：冻结status=completed的房源、当前位置、当前时间和正在执行路段，更新剩余房源窗口后重新调用同一个 optimizeRoute()；不得维护两套独立排序逻辑。

15. 每次计算都必须输出explanations和riskCodes；至少支持 appointment_conflict、time_window_conflict、late_risk、end_time_exceeded、address_unresolved、taxi_budget_exceeded、transit_detour。

参考伪代码：optimizeRoute(properties, settings, matrix) → normalizeWindows → searchFeasibleOrdersWithPruning → enumerateModePlans → simulateFullTimeline → lexicographicRank → extractAndDedupe(cheapest, recommended, fastest)。

### 17.4 地图与路线服务解耦

V0.1使用MockTravelTimeProvider返回完整模拟TravelEdge（公共交通时间/费用/换乘/步行＋打车时间/费用），先验证时间窗口、路线顺序、交通方式联合优化和三方案输出。

V0.2替换为AmapTravelTimeProvider，通过高德地图API完成地址解析、坐标获取、公共交通路线及驾车/打车时间查询；费用字段按API可用性获取或估算，并明确dataStatus。

路线排序逻辑不得直接写死在地图API调用中；地图服务只负责生成TravelEdge，排序引擎独立封装并只读取矩阵，便于Mock、单元测试及后续替换供应商。

### 17.5 状态与本地存储

V0.1使用LocalStorage保存房源、行程条件、交通矩阵缓存、三个RouteOption、当前已采用路线和看房记录；刷新页面后必须恢复最近一次有效状态。

修改地址、时间窗口、看房时长、出发/结束时间、交通策略或打车预算后，原路线标记为stale；重新计算前不得把旧结果当作最新路线。

重排方案使用draftRoute单独保存；只有点击“采用新方案”后才覆盖currentRoute，“暂不采用”必须保持currentRoute不变。

### 17.6 开发验收用例

用例1：2个固定时间预约且时间充足，应生成无冲突路线并保留默认缓冲。

用例2：存在13:00—15:00时间窗口房源时，应能够在窗口内选择最合适到达时间，而不是把它当成完全固定或完全灵活。

用例3：“17:00前看完”且看房时长30分钟时，最晚开始时间应转换为16:30；修改看房时长后窗口同步重算。

用例4：固定预约之间存在可用空档，应能插入灵活/宽窗口房源且不导致下一预约迟到。

用例5：公共交通28分钟但换乘2次、步行900米、buffer=5分钟，与地铁直达31分钟且buffer=15分钟相比，应优先更低风险方案。

用例6：默认“公共交通优先，必要时打车”下，某路段公交预计迟到而打车可准时，应生成avoid_late打车推荐并展示费用和节省时间。

用例7：某路段公交55分钟、打车18分钟且满足内部绕行阈值，应生成transit_detour候选，但若打车预算不足则不得出现在可采用推荐方案中。

用例8：一段打车可使额外1套房在最晚结束前完成，应生成unlock_extra_viewing解释，并在推荐方案比较中体现完成数量优势。

用例9：预算¥60时应比较至少全公交、单段打车和两段打车组合，最终结果按完整时间轴而非单段分钟/元选择。

用例10：同一房源顺序因不同交通方式组合导致可行性不同，优化器必须允许交通方式反向改变最终房源顺序。

用例11：必看房源导致超过最晚结束时间，应保留并标记冲突；非必看偏远房源可计算路线机会成本但不得静默移除。

用例12：两套同一中介房源仅在高层指标等价且时间差阈值内才优先连续安排；若会造成预约迟到则不得连续。

用例13：最省钱、推荐、最省时间三类目标得到相同路线时，应去重而不是重复显示三张相同卡片。

用例14：房源取消或改约后，已完成房源保持不变；从当前位置和当前时间对剩余房源重新调用同一优化器。

用例15：当前看房超时导致高风险节点触发时，如预生成Plan B可恢复可行性，应优先展示Plan B；否则再执行完整重排。

用例16：地址或公共交通数据无法解析时，不得伪造路线；若只有打车数据且策略允许，可生成明确标记的数据降级方案。

用例17：仅有1套房源时提示至少添加2套，不生成多房源路线。

用例18：房源跨多个日期时要求用户先选择本次规划日期，不混合生成单日路线。
