# 租房看房路线规划｜MVP产品需求文档 PRD

版本： V1.2

产品阶段： MVP真实场景验证

产品形态： 移动端优先网页（Next.js）；本轮不开发原生App，微信小程序待真实验证后再评估

文档目标： 明确第一版产品功能、业务规则、异常状态、数据埋点和验收标准，为交互设计、开发、测试及AI辅助编程任务拆解提供依据。

## 一、产品概述

### 1.1 产品背景

用户在1—2天内集中看多套房时，需要同时处理：

- 多个房源地址；

- 固定时间、时间范围或灵活的看房时间；

- 地点之间的交通时间；

- 不同房源的优先级；

- 最晚结束时间；

- 临时改约、取消和看房超时。

目前这些信息通常分散在租房平台、微信、中介消息、地图软件和备忘录中。用户需要反复切换工具、手动计算路线，容易出现明显折返、迟到、预约冲突和信息遗忘。

### 1.2 产品定位

面向集中看房场景的行程协调与决策工具。

产品不提供房源交易，也不替代地图导航，主要负责：

- 整理分散房源和预约信息；

- 生成基本可执行的看房计划；

- 展示路线、时间轴和推荐理由；

- 在行程变化后协助重新安排；

- 支持轻量看房记录。

核心规划能力：用户提供可用看房日期和每个日期的可用时段，系统在预约日期、时间窗口、必看程度、结束时间和打车预算等约束下，决定实际启用哪些日期、把房源分配到允许的日期，并对每个启用日期联合优化“房源顺序＋交通方式”，生成可执行、公共交通效率高且成本可控的整体看房计划。

### 1.3 产品价值

帮助用户完成：

从“我有很多分散在不同日期的房源和预约”，到“我知道需要使用哪些可用日期，以及每天按照什么顺序、什么时间、用什么交通方式去看房”。

## 二、产品目标

### 2.1 MVP核心目标

验证用户是否愿意：

- 录入真实看房所需的4—8套房源和可用日期；4—8套是V0.1A核心场景与性能目标，不是产品、引擎或输入校验的硬上限；

- 提交真实的预约和时间约束；

- 采用系统生成的整体计划，或只进行小幅修改；

- 在真实看房过程中继续查看路线中心；

- 发生临时变化时使用动态重排；

- 下一次集中看房时继续使用产品。

### 2.2 非目标

MVP阶段不解决：

- 房源搜索和房源交易；

- 自动联系中介或自动预约；

- 完整实时导航；

- 租房合同审核；

- 支付、定金或租金交易；

- 多人协作；

- 复杂房源评分模型；

- AI自动选择最终租赁房源；

- 完整租房财务管理。

## 三、目标用户

### 3.1 核心用户

- 初到陌生城市的实习生、毕业生和年轻职场人；

- 通常计划在1—2天内集中看4—8套房；V0.1产品界面可暴露最多3个可用日期，但3天不是永久领域上限；

- 同时与多个中介或公寓方沟通；

- 至少存在一套固定时间预约；

- 不熟悉当地地理位置和交通时间；

- 当前使用微信、地图、截图或备忘录手动规划。

### 3.2 核心使用场景

场景A：看房前规划

用户收集了多套房源，希望提供可用日期与每日可用时段，由系统决定实际启用日期和房源日期分配，再为每个启用日期生成可按时执行的看房顺序，并识别值得打车的关键路段。

场景B：看房当天执行

用户通过路线中心先确认整体计划和当天路线，再查看下一站、交通方式、预计到达时间和预约风险。

场景C：临时变化

中介临时改约、房源取消、看房超时或用户需要提前结束，用户需要快速重新安排。

场景D：看房后记录

用户希望在不填写长表格的情况下，记录最容易遗忘的房源印象。

## 五、核心流程

### 5.1 正常主流程

添加房源 → 设置可用日期与行程条件 → 生成看房计划 → 路线中心 → 按启用日期开始看房

### 5.2 临时变化分支

路线中心 → 行程有变化 → 选择变化类型 → 输入变化信息 → 查看重排方案 → 采用 / 自己调整 / 暂不采用

### 5.3 房源记录分支

路线中心 → 点击具体房源 → 房源详情 → 完成看房 → 快速记录 → 返回路线中心

临时变化和房源记录均为按需入口，不作为正常主流程中的固定步骤。

## 六、模块一：房源录入

### 6.1 功能目标

帮助用户尽可能低成本地将分散房源整理到同一个计划中。

### 6.2 页面名称

添加要看的房源

### 6.3 录入方式

MVP支持以下方式：

| 录入方式 | P级 | 说明 |
| --- | --- | --- |
| 手动添加 | P0 | 用户填写地址；房源名称由地址自动生成，可选修改；补充看房时间窗口和房源重要程度 |
| 粘贴地图地址 | P0 | 系统识别并标准化地址，用户补充看房时间窗口和房源重要程度 |
| 粘贴聊天内容 | P0 | 尝试提取地址和看房时间并预填，用户只补充缺失信息 |
| 粘贴房源链接 | P1 | 可保存链接，无法解析时要求手动补充 |

MVP不要求自动解析所有租房平台链接。

### 6.4 房源字段

前置字段（生成路线前）

- 房源地址；

- 看房时间窗口：固定时间 / 时间范围 / 时间灵活 / 暂未确认；

- 房源重要程度：必看 / 有时间再看（默认“有时间再看”）。

看房时间规则

- 固定时间：必须在该时间到达；原始输入保留固定时间语义，针对目标日期标准化后 earliestStart = latestStart；

- 时间范围：例如13:00—15:00均可到达；原始输入保留显式开始范围，针对目标日期标准化后形成 earliestStart / latestStart 边界；

- 时间灵活：可在最终确认的允许日期中分配；分配到某日后，使用该日可用时段作为窗口并允许系统前后调整。无日期的未确认房源如何确定允许日期仍属于待决策事项；

- “17:00前看完”等结束型表达：根据预计看房时长倒推最晚开始时间；

- 暂未确认：可保留在计划中并标记“需确认”，不作为必须满足的固定时间约束。

固定时间 / 时间范围附加字段

- 预约日期；

- 最早可开始时间；

- 最晚可开始时间（固定时间与最早时间相同）；

- 房源名称：由地址自动生成，可选修改。

- 单套预计看房时长：默认30分钟，可后续单独修改。

日期约束规则

- 固定日期预约只能安排在该日期；

- 具有有限可选日期的房源只能安排到其允许日期之一；

- 灵活房源可在最终确认的允许日期中分配；

- 系统只能使用用户提供的可用日期，不得为了恢复可行性自行增加日期。

后续可补充字段（不在生成路线前要求填写）

- 房源链接；

- 月租；

- 联系人；

- 联系方式；

- 备注；

- 中介 / 带看人（选填，用于信息录入和留存；当前V0.1A不参与路线排序）；

### 6.5 房源卡片信息

每张房源卡片展示：

- 房源名称；

- 地址；

- 预约状态；

- 固定预约时间；

- 必看标签；

- 编辑；

- 删除。

### 6.6 业务规则

- 至少添加2套房源后，才能生成多房源路线。

- 房源地址必须成功识别，或由用户手动选择候选地址。

- 固定时间或时间范围必须能够针对目标日期标准化为有效的 earliestStart / latestStart 开始窗口；窗口结束不得早于窗口开始。

- 房源名称不作为前置必填，系统根据标准化地址生成默认名称。

- 单套预计看房时长默认30分钟，用户未修改时直接使用默认值。

“17:00前看完”等结束型约束在排序前根据看房时长转换为最晚开始时间；看房时长修改后必须重新计算对应窗口。

- 联系人、联系方式、月租和备注均不阻塞路线生成。

中介 / 带看人信息不阻塞路线生成，可录入并留存；当前V0.1A不将同一中介连续性用于路线排序。

- 必看房源不会被系统自动移除。

- 重复地址允许保存，但系统需要提示“可能为重复房源”。

- 删除房源前需要二次确认。

- 修改固定预约后，已经生成的路线标记为“需要重新计算”。

### 6.7 地址识别状态

识别成功

显示标准化地址，用户可确认或修改。

多个候选地址

显示候选列表，由用户选择。

无法识别

提示：

暂时无法识别这个地址，请补充小区名称、道路或门牌号。

聊天内容部分识别

系统将识别出的内容预填，未识别字段由用户补充，不要求重新填写全部信息。

### 6.8 页面操作

主按钮：

下一步：设置行程

按钮可用条件：

- 至少存在2套有效房源；

- 所有房源地址已经确认；

- 固定预约信息完整。

### 6.9 验收标准

- 用户可以添加、编辑和删除房源；

- 用户可以设置固定时间、时间范围、时间灵活和暂未确认，并正确保存为可计算的时间窗口；

- 系统能够阻止地址为空的房源进入路线计算；

- 系统能够识别明显重复地址并提示；

- 修改房源后数据能够正确保存；

- 用户退出再返回时，已添加内容不丢失。

- 用户无需填写房源名称、租金、联系人或备注即可进入行程条件设置。

- 未单独设置看房时长时，系统按30分钟默认值参与路线计算。

## 七、模块二：行程条件设置

### 7.1 功能目标

获取生成可执行整体看房计划所需的可用日期、每日可用时段、交通和房源重要程度约束。用户提供可能出行的日期，但不需要预先决定最终使用几天。

### 7.2 页面名称

设置可用日期与看房条件

### 7.3 输入字段

| 字段 | 必填 | 默认值 |
| --- | --- | --- |
| 可用看房日期 | 是，至少1个 | 可提示最近固定预约日期，但须由用户确认 |
| 每个日期的可用时段 | 是 | 09:00—18:00，可逐日修改 |
| 出发地点 | 是 | 当前定位或用户手动填写 |
| 单套预计看房时长 | 否 | 30分钟（系统默认，可修改） |
| 交通策略 | 是 | 公共交通优先，必要时打车 |
| 打车预算 | 否 | 未设置；可选不限制 / ¥50 / ¥100 / 自定义 |
| 提前为固定预约预留多少时间 | 否 | 15分钟（默认） |
| 时间灵活的房源可以前后调整 | 否 | 默认允许 |
| 少换乘 / 少走路 / 不骑远距离 | 否 | 默认不选 |
| 最多启用天数 | 否 | 默认不限制用户提供日期中的选择数量 |
| 必须完成日期 | 否 | 未设置 |

V0.1产品界面可允许用户提供最多3个可用日期，但这是发布与界面边界，不是永久领域限制。底层日期集合不得设计为固定3项；未来支持更多日期不应要求重写规划规则。

用户提供三个日期时，系统可以只启用其中两个。用户只提供一个日期时，系统只能使用该日期。最多启用天数和必须完成日期是附加约束，不替代系统对实际启用日期的判断。

这两项是已批准产品合同中的可选计划约束；当前源代码尚未实现，具体引擎工作按 `docs/CORE_ENGINE_BACKLOG.md` 中CE-17 / CE-20的既有范围执行。

每个日期除可用时段外，是否还允许单独设置出发地、交通策略、缓冲、打车设置和偏好，属于多日输入合同的待决策事项，本PRD不在此预设答案。

### 7.4 交通策略

用户不需要逐段提前选择交通方式，而是先选择整体策略：

- 尽量公共交通：主方案原则上使用公共交通；仅当公共交通无法满足时间窗口时，在备选方案中提示必要打车；

- 公共交通优先，必要时打车（默认）：系统主动比较各路段公共交通与打车，仅在避免迟到、公共交通明显绕行或能够释放额外看房时间时优先推荐打车；

- 效率优先，可灵活打车：在适用预算允许范围内更积极使用打车，以提高单日完成房源数或缩短结束时间。

允许打车时，用户可设置打车预算；不要求填写“节省多少分钟才值得打车”“最多换乘几次”等高级阈值。多日计划使用一份共享预算还是每日独立预算仍是Decision Gate，当前不得擅自解释。未填写预算保持“未设置”状态，具体交通政策在对应任务中决定。

### 7.5 业务规则

- 每个可用日期的最晚结束时间必须晚于该日最早出发时间。

- 固定时间或时间窗口必须按其日期与可行区间安排，系统不提供“是否优先”的普通开关。

- 固定日期预约不能跨日期移动；日期受限房源只能安排到其允许日期之一。

- 时间灵活及较宽时间窗口房源可以在其允许日期之间分配；进入某个单日路线后，可以在不违反该日窗口上限的前提下前后移动。

- 必看房源必须尽量安排；无法安排时必须明确提示。

- 固定预约前默认预留15分钟缓冲。

- 看房时长适用于全部房源，用户可在房源详情中单独修改。

- 用户必须选择一种交通策略；打车预算未填写时保留“未设置”状态，不在此处静默等同于“不限制预算”。

- 用户未设置看房时长时使用30分钟默认值。

- “少换乘 / 少走路 / 不骑远距离”仅用于更高层目标基本一致的方案排序，不得覆盖时间窗口、必看、最晚结束等硬约束。同一中介连续性属于Case 12 / P1，当前V0.1A不参与排序。

### 7.6 条件冲突提示

固定预约早于出发时间

提示：

第一套固定预约早于当前出发时间，请提前出发或修改预约。

结束时间过早

提示：

当前结束时间可能无法完成所有房源，仍可生成方案并查看取舍建议。

时间窗口无效

提示：

最晚可开始时间早于最早可开始时间，请检查看房时间设置。

固定预约日期不在可用日期中

提示：

某套房源的固定预约日期不在你提供的可用日期中。请添加该日期、修改预约或保留冲突。

多个预约跨日期本身不是产品错误。只要相关日期由用户提供为可用，系统应将固定预约保留在各自日期并生成多日计划。

仅有一个可用日期且时间不足

提示：

当前提供的日期无法安排全部重要房源。系统不会自动添加其他日期；你可以查看冲突或部分结果，并补充另一个可用日期。多日结果何时属于成功、部分成功或失败，留待对应Decision Gate决定。

### 7.7 页面操作

主按钮：

生成看房计划

点击后：

- 保存全部条件；

- 进入计划计算状态；

- 成功后进入路线中心；

- 失败时展示具体原因和解决方式。

### 7.8 验收标准

- 所有必填字段具有校验；

- 日期或每日时间逻辑错误时不能直接生成计划；

- 用户可以提供一个或多个可用日期及每个日期的可用时段；

- 用户无需选择确切启用天数，系统可以少用但不能使用未提供的日期；

- 用户可以选择整体交通策略，并可在允许打车时设置打车预算；

- 系统能够正确读取必看和固定预约房源；

- 系统能够正确读取并转换固定时间、时间范围、灵活时间和结束型时间约束；

- 用户修改条件后可以重新生成计划。

### 7.9 用户文案约束

- 界面避免使用“锁定顺序、时间预算、优先级、路线偏好”等抽象术语，统一使用以下生活化表达：

- “锁定时间” → “必须在这个时间到达”；

- “锁定顺序” → “必须先看这套”；

- “时间预算” → “最晚几点结束”；

- “优先级” → “必看 / 有时间再看”；

- “路线偏好” → “少换乘 / 少走路 / 不骑远距离”。

- “可接受交通方式” → “看房时更希望怎么出行？”；“固定/灵活”内部统一使用日期资格和单日时间窗口计算，但界面继续使用生活化表达。

## 八、模块三：看房计划生成

### 8.1 功能目标

系统默认不追求单纯的“最短路线”。多日规划先从用户提供的可用日期中选择启用日期并分配房源；随后在每个启用日期内，根据预约时间窗口、必看程度、结束时间和适用的打车预算联合优化“房源顺序＋交通方式”。系统最后汇总各单日路线并比较整体计划。

多日规划与单日路线优化是两个正式分离的层次：

可用日期与每日可用时段 → 校验可用日期 → 推导每套房源的允许日期 → 搜索日期分配候选 → 分别优化各启用日期的单日路线 → 汇总整体指标 → 比较整体计划。

固定日期预约只能分配到固定日期；日期受限房源只能在允许日期中分配；灵活房源可在最终确认的允许日期中分配。系统不得启用用户未提供的日期。

### 8.2 输入数据

整体计划生成读取：

- 用户提供的可用日期及每个日期的可用时段；

- 可选的最多启用天数和必须完成日期；

- 出发地点以及适用于单日路线的开始/结束条件；

- 房源标准地址和坐标；

- 房源的原始看房时间输入，以及针对目标日期标准化后的 earliestStart / latestStart 开始窗口；

- 房源重要程度（必看 / 有时间再看）；

- 预计看房时长；

- 交通策略和可选打车预算；

- 固定预约缓冲时间；

- 中介 / 带看人（选填）；

- 预计算的两两地点公共交通与打车时间、费用、公共交通换乘次数和步行距离。

每个单日路线优化调用只接收同一个目标日期内已分配且允许的房源。不同日期同时出现在整个多日计划中是有效行为；不同日期混入同一次单日路线优化调用才是单日输入错误。

### 8.3 时间窗口统一模型

时间窗口标准化针对一个目标日期执行。固定时间的两个值相同；时间范围直接使用上下限；“下午均可”等生活化输入按产品预设转换；“17:00前看完”等结束型约束根据预计看房时长倒推最晚开始时间。固定日期与目标日期不一致时，该房源对该日是“不允许安排”，而不是时间格式错误。暂未确认房源可参与候选排序，但不得作为必须满足的固定时间锚点；无日期的未确认房源如何确定允许日期仍为Decision Gate。

每个日期有独立的同日时间轴：日期使用严格 `YYYY-MM-DD`，时间使用严格 `HH:mm`，内部分钟值为0—1439。日期可以不连续；单日路线不得跨越或静默回绕午夜，也不得使用一个跨多日的累计分钟轴。相关确定性校验将在后续CE任务实现，当前源代码尚未实现这些能力。

### 8.4 交通矩阵

交通获取层应在优化前预计算“所需起点＋相关房源”之间的交通矩阵。Provider、外部API、失败处理和矩阵构建属于路线引擎外部的交通数据层；单日路线优化器和多日规划搜索只读取预计算矩阵，不得调用Provider或地图API。每条交通边至少包括公共交通时间、公共交通费用、换乘次数、步行距离，以及打车时间和预计费用。

### 8.5 硬约束与时间锚点

硬约束优先于一切效率和成本指标，包括：时间窗口可满足、必看房源原则上保留、不能早于最早出发、尽量不晚于最晚结束、已完成房源不可重排、看房时长和固定预约缓冲必须计入时间轴。固定时间或较窄时间窗口优先形成时间锚点。

### 8.6 候选顺序与空档插入

单日路线以时间锚点为骨架。判断某个房源能否放入某个空档属于纯可行性规则；决定尝试哪些房源、哪些空档以及尝试顺序属于候选搜索。候选房源只有满足以下可行性条件时才允许插入：

当前房源结束时间 + 去候选房源交通时间 + 候选房源看房时长 + 去下一时间锚点交通时间 + 安全缓冲 ≤ 下一时间窗口的最晚允许时间。

初始搜索可使用DFS / 回溯探索固定预约之间的空档并调用独立可行性评估器剪枝。搜索策略决定尝试哪些候选，不能定义时间窗口、风险、排名或解释规则。4—8套是V0.1A场景和性能目标，不是硬上限；未来10—15套等更大输入应优先通过替换为Branch and Bound、Beam Search或其他策略扩展，具体切换阈值仍未决定。

### 8.7 公共交通可执行风险

公共交通不只使用API给出的预计时间，还计算规则型风险。V1建议采用可配置分值：换乘≥2次 +2；步行≥800米 +1；到下一时间窗口的缓冲<10分钟 +2、10—15分钟 +1；若API能够识别高公交占比或复杂接驳，可额外 +1。riskScore 0—1=低、2=中、≥3=高。真实用户测试后再校准阈值。

当两个方案交通时间接近时，应优先风险更低、缓冲更充足的方案，使目标从“理论最快”变为“最可能按计划完成”。

### 8.8 房源顺序＋交通方式联合优化

系统不能长期采用“先排顺序、再选公交/打车”的串行逻辑，因为交通方式可能改变最佳房源顺序。交通方式是否可用、是否符合策略、是否满足适用预算属于业务规则；具体枚举哪些合法组合、以什么顺序探索属于可替换搜索策略。每个被评估的顺序与模式组合都必须重新模拟完整单日时间轴。

- 尽量公共交通：主方案不主动加入打车；若公共交通无法满足关键时间窗口，可在备选/Plan B中提示必要打车。

- 公共交通优先，必要时打车：默认基线比较覆盖0段、1段、2段打车及适用预算允许的关键组合；这不是永久的通用最大深度。

- 效率优先，可灵活打车：可比较更多打车组合，仍受总预算约束。

V0.1A的4—8套核心场景可在预计算交通矩阵后本地枚举模式组合，但该数量不是输入限制，也不得为每个组合重新请求Provider或地图API。

### 8.9 关键打车路段判断

打车不是因为“更快”就推荐，而是在对应单日路线的边际价值明显时才推荐。V1优先识别三类场景：

- 避免迟到：公共交通无法满足下一时间窗口，而打车可以满足；

- 公共交通明显绕行：首版可配置为“打车节省≥25分钟，且公共交通时间/打车时间≥1.8”或公共交通存在多次换乘；该阈值仅为内部默认值，不要求用户填写；

- 释放额外看房容量：某段改打车后，能够在最晚结束时间前多安排至少1套房，或恢复必看房源的可行性。

系统同时计算基础性价比（额外费用对应的节省时间）和行程价值（避免迟到、增加完成数量、保证必看、降低高风险交通、提前结束）；最终以行程价值优先，不简单使用“分钟/元”排序。

### 8.10 路线机会成本与同一带看人

路线机会成本：对非必看房源可额外比较“包含该房源 vs 不包含该房源”的最优结果，输出新增交通时间、结束时间变化和是否挤掉其他房源。必看房源只提示影响，不自动移除。该能力为P1，不阻塞首版核心排序。

同一中介 / 带看人连续性属于Case 12 / P1，当前V0.1A不参与路线排序。未来实现时，只有在硬约束、完成数量、风险等更高层指标基本相同时，才可作为低层并列偏好；建议V1使用“总交通时间差≤10分钟”作为可配置的同等方案判定阈值。

### 8.11 候选方案分层比较

单日候选路线采用字典序 / 分层比较，不将所有指标粗暴加权为一个总分：

- 第一层：硬约束——时间窗口满足、必看房源保留、最晚结束；

- 第二层：完成效率——尽量完成更多房源并充分利用时间空档；

- 第三层：可执行性——降低迟到风险并保留合理缓冲；

- 第四层：交通效率——减少总交通时间和明显折返；

- 第五层：成本效率——公共交通优先、关键段合理打车、不超过预算；

- 第六层：体验——少换乘、少步行、少等待。同中介连续性在当前V0.1A不参与此层排序。

### 8.12 输出三类方案

单日路线从候选结果中提取并去重三类方案：

- 最省钱：打车支出最低，通常以公共交通为主；

- 推荐方案：默认突出，在预约可执行和完成数量优先的前提下，平衡交通时间、迟到风险与打车成本；

- 最省时间：在用户交通策略和预算允许范围内尽量提前结束或完成更多房源。

每个单日方案至少输出：房源顺序、每段交通方式、预计出发/到达/看房时间、可完成房源数、总交通时间、预计结束时间、预计打车费用、公共交通风险和关键解释。若三类目标得到相同结果，只显示去重后的方案。多日最终结果是一个推荐整体计划、三种整体方案还是“整体推荐＋每日备选”，仍为Decision Gate，本文不预设答案。

### 8.13 高风险节点Plan B（P1）

排序完成后识别全程最紧张的1—2个节点（例如buffer<15分钟或公共交通risk=高），预生成一个轻量备用方案：优先尝试将关键路段改为打车；仍不可行时，将非必看/宽时间窗口房源后移或跳过。Plan B仍调用同一排序规则，不另建一套算法。

### 8.14 路线计算状态

计划计算中

展示：“正在分配可用日期并比较每日路线……”；超过5秒补充“房源较多，正在评估可执行计划”。

计算成功

进入路线中心并展示推荐整体计划及各启用日期。整体方案形态按尚未关闭的Decision Gate执行。

部分成功

当没有计划能够同时满足全部要求时，可输出最接近可执行的计划，并明确标记日期资格、每日时间窗口、结束时间、必看或预算冲突。成功、部分成功和失败的精确多日结果不变量仍为Decision Gate。

计算失败

在地址/交通数据缺失、基础输入无效或没有可计算日期等情况下给出具体修复入口；精确的多日失败边界由后续结果合同Decision Gate决定。

### 8.15 推荐解释规则

关键解释至少覆盖：为什么启用某个用户提供的日期、为什么某房源被安排到该允许日期和时间段、为什么某段建议打车，以及某套房的机会成本（若已计算）。只有用户提供且房源允许的日期才能成为“移至其他日期”的建议。示例：“B房安排在周日，因为周六无法在不影响14:00预约的前提下完成”“A→B公共交通需58分钟且换乘2次，打车约¥29可节省37分钟”“本段改打车可使当日多完成1套房”。

### 8.16 验收标准

- 相同输入和交通矩阵下，排序结果保持确定性；

- 相同多日输入和交通矩阵下，启用日期和日期分配保持确定性；

- 所有启用日期都属于用户提供的可用日期，固定预约不跨日期移动；

- 每个单日时间轴独立单调，不跨越或静默回绕午夜；

- 任何推荐方案都不得无提示违反固定时间或明确时间窗口；

- 必看房源不得被系统静默删除；无法满足时必须输出冲突；

- 系统能够主动利用预约空档插入可行房源；

- 公共交通风险会影响同等时间方案的排序；

- 默认交通策略下能够比较至少全公交、单段打车和两段打车组合；

- 推荐打车时必须说明预计费用、节省时间和行程价值；

- 能够输出最省钱、推荐、最省时间方案并对重复结果去重；

- 每段交通时间和看房时长必须进入完整时间轴计算；

- 地图编号与时间轴编号一致；冲突情况下仍给出可理解的处理建议。

## 九、模块四：路线中心

### 9.1 功能目标

作为整体看房计划的核心页面，帮助用户理解系统实际启用了哪些可用日期、房源如何按日分配，并查看、调整和执行每个启用日期的单日路线。

### 9.2 页面名称

看房计划与每日路线

### 9.3 顶部摘要

先展示整体计划摘要：

- 用户提供的可用日期与系统实际启用日期；

- 启用天数和未使用日期；

- 每日房源数量、总体预计完成数量和关键冲突；

- 系统为何使用这些日期或把某套房安排到某日的解释。

再为当前选中的启用日期展示单日摘要：

- 预计出发时间；

- 预计结束时间；

- 房源数量；

- 总交通时间；

- 是否存在风险。

- 当前方案类型（最省钱 / 推荐 / 最省时间）；

- 预计打车费用；

- 相对全公交的预计节省时间。

示例：

09:10出发 · 17:20结束 · 4套房 · 交通约1小时48分钟

### 9.4 整体计划与单日方案切换

路线中心支持在启用日期之间切换，并按日期显示对应单日路线。每个启用日期内可展示最省钱、推荐和最省时间方案卡片；推荐单日方案默认选中。每张单日卡片展示预计结束时间、完成房源数、总交通时间、预计打车费用和主要风险；重复方案不重复展示。

最终多日结果是否同时提供多种整体计划、只提供一个推荐整体计划或采用“整体推荐＋每日备选”，仍为Decision Gate。本节不把任何一种结构写成已确认产品行为。

切换方案只改变当前展示和待采用方案，不应在用户明确点击“采用此方案”前覆盖已确认路线。

### 9.5 时间轴区域

每个启用日期拥有独立的单日时间轴。时间轴仍是该日的主要信息结构，每套房源展示：

- 编号；

- 房源名称；

- 预计到达时间；

- 预约或看房时间；

- 交通方式和时长；

- 预约类型；

- 当前状态；

- 推荐理由；

- 风险提示；

- 公共交通风险等级；

- 若建议打车：预计费用、节省时间和推荐原因；

- 导航按钮；

- 更多操作。

### 9.6 地图区域

地图按当前启用日期展示：

- 出发点；

- 房源编号点位；

- 点位之间的路线连线；

- 当前或下一套房；

- 风险房源标记。

编号必须与时间轴一致。

地图只承担空间理解和路线方向表达，不替代时间轴。

| 状态 | 说明 |
| --- | --- |
| 待出发 | 尚未开始前往 |
| 前往中 | 用户已点击导航或开始行程 |

导航

### 9.9 手动调整

用户可以：

- 拖动时间灵活房源；

- 修改预计停留时间；

- 切换单段交通方式或整体交通策略；

- 暂时移除房源；

- 修改最晚结束时间。

上述调整默认作用于当前单日路线。未来是否允许通过手动调整把房源跨启用日期移动，不在当前Core Engine范围内预设。

固定预约房源不可直接拖动；如需调整，先修改预约时间。

用户手动调整房源顺序或交通方式后，系统必须重算全部后续时间轴，并更新完成数量、迟到风险、结束时间和打车费用；不得只改界面顺序。

调整过程中实时显示：

- 是否会迟到；

- 新的结束时间；

- 总交通时间变化；

- 是否产生冲突。

- 标记已到达；

- 跳过本套；

- 房源取消；

- 查看详情；

- 删除出本次行程。

### 9.11 验收标准

- 用户能够清楚看到下一套房；

- 用户能够看到整体启用日期、每日房源分组以及当前查看日期；

- 用户能够理解并切换最省钱、推荐和最省时间方案；

- 每个启用日期内地图和时间轴顺序完全一致；

- 点击每套房源均能进入详情；

- 用户可以发现“行程有变化”入口；

- 用户可以进入手动调整；

- 用户能够看到关键打车路段的费用、节省时间和原因；

- 房源状态变化后页面即时更新；

- 导航按钮能够唤起地图；

- 页面刷新后当前进度不会丢失。

## 十、模块五：临时变化与重排

### 10.1 功能目标

在预约、房源或用户时间发生变化后，帮助用户快速理解影响并做出决策。

### 10.2 入口

路线中心中的：

行程有变化

房源卡片更多菜单也可直接进入对应变化类型。

### 10.3 MVP支持的变化类型

P0

- 房源预约时间改变；

- 房源取消或已租出；

- 当前看房时间超过预计。

P1

- 新增房源；

- 用户出发时间改变；

- 用户需要提前结束；

- 交通方式临时变化。

### 10.4 变化录入

预约时间改变

用户选择：

- 发生变化的房源；

- 新预约时间；

- 是否仍然必看。

房源取消

用户选择：

- 取消的房源；

- 是否从当前日期的单日路线移除。

看房超时

用户填写或选择：

- 实际结束时间；

- 是否已经出发前往下一套。

### 10.5 重排规则

当前已确认的重排语义是单日范围：重排与该日首次路线生成复用同一套单日优化规则；系统冻结已完成房源、当前位置、当前时间和正在执行中的路段，仅更新该日剩余房源的时间窗口和交通候选。未来集成API的目标名称是 `optimizeDayRoute()`，该函数要到CE-16才实现。

如果当天变化影响未来日期的灵活房源，是否允许跨启用日期重新分配仍是Decision Gate，属于CE-21之后的动态重排工作，本PRD不在当前阶段决定。

- 只重新计算受变化影响的部分；

- 已经完成的房源保持不变；

- 当前正在进行的行程尽量保持；

- 新固定预约优先保证；

- 重排继续比较公共交通与打车组合，并受原交通策略及剩余打车预算约束；

- 灵活房源可以后移、前移或建议移除；

- 若预生成Plan B可直接恢复可行性，优先展示Plan B；否则再生成新的最省钱 / 推荐 / 最省时间候选。

- 不自动接受新方案；

- 用户必须做出明确选择。

### 10.6 重排结果页面

页面只重点展示真正发生变化的内容。

每项变化使用“原方案 → 新方案”表达：

- 到达时间；

- 看房时间；

- 房源顺序；

- 交通方式；

- 结束时间；

- 预计打车费用及相对原方案变化；

- 是否新增冲突。

未变化内容只显示一句：

其他房源的时间和顺序不受影响。

### 10.7 用户决策

采用新方案

- 保存重排结果；

- 更新地图和时间轴；

- 返回路线中心；

- 显示“行程已更新”。

自己调整

- 进入手动调整；

- 用户拖动灵活房源；

- 保存后返回路线中心。

暂不采用

- 不保存新路线；

- 返回原路线中心；

- 保留原方案；

- 可显示风险提醒。

### 10.8 冲突处理

若重排后仍然无法满足全部预约，系统提供选项：

- 移除一套非必看房；

- 延后灵活房源；

- 修改最晚结束时间；

- 联系中介改约；

- 保留冲突并继续。

### 10.9 验收标准

- 已完成房源不会被重新排序；

- 页面只突出变化部分；

- “采用、自己调整、暂不采用”含义清晰；

- 暂不采用后原路线保持不变；

- 采用后地图和时间轴同步更新；

- 采用后剩余打车预算、风险等级和Plan B同步更新；

- 所有路径均能返回路线中心；

- 重排不能出现无提示删除房源的情况。

## 十一、模块六：简单房源记录

### 11.1 功能目标

帮助用户用约30秒记录最容易忘记的信息，不影响主行程执行。

### 11.2 入口

- 房源详情点击“完成看房”；

- 已看房源点击“补充记录”。

### 11.3 快速记录字段

必选

选填

采光不错，但临街有噪音。

### 11.4 保存逻辑

保存快速记录

补充租金与费用

稍后补充

### 11.5 基础费用记录

租金信息

- 押付方式；

- 中介费。

水电费

网络费

物业费

### 11.6 月度成本摘要

### 11.7 业务规则

- 快速记录不能设置过多必填字段。

- 用户未填写费用也可以保存看房记录。

- 选择“淘汰”后不自动从当日路线删除房源。

- 已保存的记录可以修改。

- 支持稍后补录。

- 记录保存后，路线中心显示“已记录”。

### 11.8 验收标准

- 用户能够在不填写费用的情况下保存记录；

- 候选状态保存后正确展示；

- 用户可重新进入并修改记录；

- 稍后补充不会导致已有信息丢失；

- 费用计算只使用已知且可转换为月度金额的字段；

- 未知费用不会默认为0元。

## 十二、模块七：异常状态

### 12.1 房源录入异常

| 异常 | 提示 | 用户操作 |
| --- | --- | --- |
| 地址为空 | 请填写房源地址 | 返回编辑 |
| 地址无法识别 | 暂时无法确认位置 | 选择候选或手动补充 |
| 重复房源 | 可能已添加相同房源 | 仍然添加或取消 |
| 预约信息缺失 | 请补充固定预约时间 | 返回编辑 |
| 房源过少 | 至少添加2套房源 | 继续添加 |

### 12.2 行程条件异常

| 异常 | 提示 |
| --- | --- |
| 未选择交通方式 | 请至少选择一种交通方式 |
| 固定预约日期不在可用日期中 | 请添加该可用日期、修改预约或保留明确冲突；系统不得自行启用该日期 |
| 可用日期为空 | 请至少提供一个可用看房日期 |
| 某日结束时间早于该日出发时间 | 请检查该日期的可用时段 |
| 出发地无法识别 | 请选择准确的出发位置 |
| 打车预算无效 | 请输入非负金额，或选择“不限制” |

### 12.3 路线生成异常

| 异常 | 处理 |
| --- | --- |
| 地图API不可用 | 提示稍后重试并保留输入 |
| 交通时间获取失败 | 交通数据层仅在具有明确估算来源时提供带dataStatus的估算；否则标记缺失并给出重试或修改条件入口，不得由优化器伪造数据 |
| 固定预约无法满足 | 展示冲突房源和处理建议 |
| 超过最晚结束时间 | 生成风险方案，不直接失败 |
| 某房源距离过远 | 仅可建议移至用户已提供且该房源允许的其他日期；否则说明现有可用时间不足 |
| 仅有一个可用日期且无法安排全部必看房源 | 展示现有可用时间不足及冲突/部分结果，并允许用户补充日期；不得虚构另一日期 |
| 全部路线生成失败 | 提供返回修改条件入口 |
| 公共交通数据不可用 | 无法比较时明确标记；若用户允许打车，可仅生成临时打车候选，否则提示稍后重试 |
| 打车价格数据不可用 | 仍可生成公共交通方案，但不展示费用性价比和混合交通推荐 |
| 无完全可行方案 | 输出最接近方案及违反的具体约束，不静默删除必看房源 |

### 12.4 执行过程异常

- 用户错过预约；

- 用户未点击到达但已经完成看房；

- 用户误操作跳过房源；

- 地图导航无法唤起；

- 当前时间已经晚于计划时间；

- 页面断网或刷新。

处理原则：

- 不丢失已经完成的操作；

- 允许用户手动修改状态；

- 避免强制按照理想流程操作；

- 离线情况下优先展示最近一次保存的行程。

### 12.5 保存异常

保存失败时：

- 保留本地填写内容；

- 提示重新保存；

- 不直接关闭页面；

- 避免重复创建相同记录。

## 十三、数据指标与埋点

### 13.1 核心漏斗

开始添加房源 → 完成房源录入 → 完成可用日期与条件设置 → 生成整体计划 → 进入路线中心并采用/调整计划 → 按启用日期开始行程 → 完成看房

### 13.2 核心事件

| 事件名称 | 触发时机 | 关键参数 |

| property_add_start | 点击添加房源 | 录入方式 |
| property_add_success | 成功添加房源 | 地址来源、预约类型 |

| plan_generate_fail | 整体计划生成失败 | 失败原因 |
| plan_accept | 采用推荐整体计划 | 启用日期数、是否存在风险 |

| reroute_accept | 采用重排方案 | 结束时间变化 |

| fallback_ready | 生成Plan B | triggerType、affectedPropertyIds |

### 13.3 核心指标

房源录入完成率

完成添加至少4套有效房源的用户数 ÷ 开始添加房源的用户数。

目标积极信号：≥70%。

看房计划生成成功率

成功生成整体计划的提交数 ÷ 提交计划生成的次数。

目标积极信号：≥85%。

计划采用率

采用推荐整体计划或仅进行小幅调整的计划数 ÷ 成功生成整体计划的计划数。

目标积极信号：≥60%。

推荐计划采用率：采用系统默认推荐整体计划的计划数 ÷ 成功生成整体计划的计划数；首轮主要观察，不预设硬阈值。多日结果最终展示几种整体方案仍为Decision Gate。

时间窗口准时完成率：在有效时间窗口内开始看房的已执行房源数 ÷ 已执行房源数；建议积极信号≥85%。

关键打车推荐接受率：采用系统关键打车建议的路段数 ÷ 系统产生关键打车建议的路段数；首轮作为诊断指标，不作为Go/No-Go单独阈值。

固定预约准时率

按时到达固定预约的次数 ÷ 已执行固定预约次数。

目标积极信号：≥85%。

动态重排完成率

成功完成重排并返回路线中心的次数 ÷ 提交临时变化的次数。

目标积极信号：≥70%。

房源记录使用率

保存至少一套房源记录的计划数 ÷ 完成至少一套看房的计划数。

目标积极信号：≥40%。

再次使用意愿

下一次集中看房仍愿意使用的用户比例。

目标积极信号：≥60%。

### 13.4 保护性指标

需要同步监控：

- 平均添加一套房源耗时；

- 地址识别失败率；

- 整体计划与单日路线生成平均耗时；

- 用户大幅重排路线比例；

- 固定预约迟到率；

- 因冲突而放弃整个计划的比例；

- 路线中心退出率；

- 快速记录放弃率；

- 系统推荐与用户最终顺序差异。

- 三类方案选择分布；

- 平均打车支出与公共交通路段占比；

- 高风险公共交通路段实际迟到率；

- 推荐打车段的平均节省时间和实际采用率；

- 系统预测可完成房源数与实际完成房源数差异。

## 十四、非功能性需求

### 14.1 性能

- V0.1A核心场景的普通整体计划生成目标：5秒以内；

- 交通矩阵已缓存时，4—8套房源的单日候选搜索与方案比较目标≤1秒；真实API获取时间不计入该目标。多日分配的独立性能目标和更大输入的搜索切换阈值待性能数据与Decision Gate确认。

- 超过5秒需要明确加载反馈；

- 页面主要操作响应时间目标：1秒以内；

- 输入和记录需要自动保存草稿。

### 14.2 稳定性

- 路线生成失败不能导致房源数据丢失；

- 页面刷新后恢复最近一次保存状态；

- 临时网络异常后支持重新提交；

- 防止重复生成计划和重复保存记录。

### 14.3 隐私

- 明确说明地址信息仅用于生成本次路线；

- 联系人和联系方式不默认公开；

- 不将用户行程分享给中介或第三方；

- 用户可以删除计划及相关记录。

### 14.4 可用性

- 核心主流程不超过3个主要页面；

- 快速记录必填项不超过1项；

- 所有异常提示必须提供解决操作；

- 不出现只有错误信息、没有下一步的页面。

## 十五、MVP整体验收标准

产品进入真实用户测试前，必须满足：

- 用户能够添加、编辑和删除房源；

- 用户能够设置固定时间、时间范围、时间灵活、必看及有时间再看房源；

- 用户能够提供一个或多个可用日期、每个日期的可用时段以及出发地点；

- 用户无需预先选择最终启用天数，系统实际启用日期始终是用户提供日期的子集；

- 固定预约保持原日期，灵活或日期受限房源只在允许日期中分配；

- 只提供一个日期且计划不可行时，系统不虚构新日期，并提供可操作的不足说明；

- 路线中心能够展示整体启用日期和每日分组路线，每个启用日期内地图与时间轴一致；

- 固定预约冲突能够被识别；

- 用户能够理解推荐顺序的原因；

- 系统能够分别对每个启用日期联合优化房源顺序与交通方式，并输出该日最省钱 / 推荐 / 最省时间方案；多日整体方案形态以未关闭的Decision Gate为准；

- 用户能够手动调整时间灵活房源；

- 用户可以通过路线中心进入导航；

- 关键打车推荐必须展示预计费用、节省时间和行程价值，且不超过用户设定预算；

- 用户可以提交预约变化、取消和看房超时；

- 重排结果只突出发生变化的部分；

- 用户可以采用、自己调整或暂不采用；

- 暂不采用不会覆盖原方案；

- 用户能够完成简单看房记录；

- 所有主要页面具有返回路径；

- 核心流程不存在死路；

- 核心行为数据能够被记录。

## 十七、开发实现附录（用于AI辅助编程 / Vibe Coding）

本附录用于把PRD进一步约束为可直接拆分、实现和测试的开发任务；若与前文冲突，以前文的用户规则和优先级为准。

### 17.1 页面与路由边界

添加房源页：/；负责房源地址、看房时间和房源重要程度的录入。

行程条件页：/plan/settings；未来负责可用日期、每日可用时段、出发地、交通策略、可选打车预算和出行偏好。每个日期是否支持独立出发地、策略等高级设置仍为Decision Gate。

路线中心：/plan/route；代表完整看房计划，负责启用日期概览、每日分组路线、单日方案、时间轴、地图辅助、推荐理由、风险提示、打车建议和行程状态。

手动调整：/plan/route/adjust；仅允许拖动时间灵活房源。

房源详情与记录：/property/[id] 与 /property/[id]/note；记录模块不得阻塞路线主流程。

### 17.2 核心数据对象

本PRD定义数据的产品含义；对于已实现的CE-01合同，精确TypeScript结构以 `src/lib/route/types.ts` 为准。源代码只用于说明当前实现状态；产品行为仍以本PRD为准。

当前 `Property` 是已实现的日级路线领域合同，包含身份、地址、可选展示名、可选位置标识、重要程度、时长、可选中介信息和状态等语义。原始看房时间通过结构化的 `viewingTime` 变体表达：固定时间、开始时间范围 / 某时前完成、时间灵活或暂未确认。它不是 `timeType + earliestTime + latestTime` 的扁平原始合同。CE-01已定义标准化结果的类型词汇，但从原始变体产生 earliestStart / latestStart 开始边界的行为要到CE-03才实现。

当前 `DayPlanSettings` 是已实现的单日路线设置合同，表达一个目标日期的起点、开始/结束边界、交通策略、打车预算状态、固定预约缓冲和路线偏好。CE-01.1已完成名称澄清，未改变该单日合同的字段或不变量。

当前 `RouteStop`、`SimulationResult`、`RouteCandidate` 和 `RouteOption` 是已实现的日级输出领域合同。它们分别表达某站的交通/到达/等待/看房/缓冲语义、完整时间轴模拟与汇总、带风险/指标/解释的候选路线，以及用户可见的去重选项。一个 `RouteOption` 通过已验证的 `objectiveLabels` 承载一个或多个目标标签（cheapest / recommended / fastest）；当多个目标得到同一房源顺序和交通模式时，只暴露一个选项。

当前 `DayRouteOptimizationResult` 是已实现的单日路线结果合同，区分success、partial和failure，并表达日级选项、冲突与已考虑候选数的语义。其精确状态不变量以源类型为准。CE-01.1已完成名称澄清，未改变该单日合同的字段或不变量。

交通边和预计算交通矩阵是交通数据层概念，不是当前CE-01源合同。其具体TypeScript结构由CE-05在 `src/lib/travel/` 中定义；当前PRD只要求它们能提供单日优化所需的公共交通/打车时间、费用、换乘、步行与数据状态语义。

多日输入、日期分配候选、整体指标和多日优化结果是未来合同，要到CE-17及后续任务才定义。本PRD只规定产品语义，不假定这些源类型已经存在。

`FallbackPlan` 是Plan B的P1 / 延期产品概念，当前没有源合同。行程变化和房源记录同样只在本PRD定义 `ChangeEvent` 与 `PropertyNote` 的产品语义；具体持久化或TypeScript结构尚未实现，需在后续任务中单独评审。

### 17.3 路线生成实现契约

单日路线与多日规划必须保持两个独立管线。

单日路线目标管线（集成API到CE-16才实现）：

已分配到一个 `CalendarDate` 的房源 + CE-01.1后的 `DayPlanSettings` + 预计算 `TravelMatrix`
→ 单日输入校验
→ 针对目标日期的时间窗口标准化
→ 候选顺序搜索
→ 可行性评估
→ 交通方式候选搜索
→ 同日完整时间轴模拟
→ 约束、风险和打车价值评估
→ 单日分层排序
→ 解释与单日方案提取
→ 未来 `optimizeDayRoute()`。

多日规划目标管线（具体源合同到CE-17及以后才定义）：

可用日期 + 每日可用时段 + 房源 + 可选多日约束
→ 校验可用日期
→ 推导每套房源的允许日期
→ 搜索日期分配候选
→ 对每个启用日期调用单日优化
→ 汇总整体指标
→ 整体计划排序
→ 未来 `optimizeMultiDayPlan()`。

业务规则与搜索策略必须分离：

- `canFitInGap`等空档可行性判断是纯业务规则；选择尝试哪个房源和哪个空档是搜索。
- 交通方式是否合法、路段是否可用、预算是否有效是业务规则；枚举哪些合法公共交通/打车组合是搜索。
- 时间窗口、完整时间轴、约束、风险、打车价值、指标、排序和解释都是业务规则。
- DFS / 回溯只负责候选遍历和调用纯评估器剪枝，不得定义排名、风险、解释或约束真值。
- 搜索未来可以替换为Branch and Bound、Beam Search或求解器，而不重写业务规则。

4—8套房源是V0.1A核心场景和性能覆盖，不是硬限制。当前不决定10—15套等更大计划切换搜索策略的精确阈值。

路线机会成本和同中介软约束属于P1；Plan B和动态重排属于当前Core Engine完成后的后续范围。Case 12、14、15不作为当前V0.1A完成条件。未来单日重排应复用单日路线规则，但跨日重新分配仍为Decision Gate。

详细CE状态、依赖、测试映射和定义完成条件只在 `docs/CORE_ENGINE_BACKLOG.md` 维护。

### 17.4 地图与路线服务解耦

交通数据获取位于路线引擎之外。未来建议由 `src/lib/travel/` 负责TravelTimeProvider、MockTravelTimeProvider、交通边、交通矩阵构建、provider失败处理和外部数据获取边界；具体文件在对应CE任务中确定。

V0.1A由外部交通层使用确定性MockTravelTimeProvider构建完整模拟矩阵；后续可替换为AmapTravelTimeProvider，通过高德地图API完成地址解析、坐标获取、公共交通路线及驾车/打车时间查询，费用字段按API可用性获取或估算并明确dataStatus。

`src/lib/route/` 不得导入或了解TravelTimeProvider。单日优化器只消费预计算TravelMatrix；多日规划器可以使用预计算数据编排单日优化，但不得在日期分配、路线搜索、模拟或排序中调用provider。该边界使Mock、单元测试和供应商替换不改变规划业务规则。

### 17.5 状态与本地存储

LocalStorage属于CE-21通过确定性验收并完成评审后的产品实现范围，不属于当前纯TypeScript Core Engine。未来持久化应保存完整看房计划、启用日期、每日路线、已采用结果和看房记录；具体存储合同需要单独评审。

修改地址、时间窗口、看房时长、出发/结束时间、交通策略或打车预算后，原整体计划及受影响的单日路线应标记为stale；重新计算前不得把旧结果当作最新计划。

未采用的重排结果应与当前已接受的整体计划分开保存；只有点击“采用新方案”后才能覆盖已接受计划，“暂不采用”必须保持已接受计划不变。具体持久化字段名未定。
